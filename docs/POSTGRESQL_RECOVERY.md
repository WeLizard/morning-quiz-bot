# PostgreSQL: восстановление классического квиза и очистка

Локальная реализация MQB-001 от 2026-08-30. Сервер не переключён.
Классический квиз остаётся игрой в Telegram-чате; Mini App для него не требуется.

## Что сохраняется

`ClassicSessions` меняет только строку `classic:<chat_id>` в `quiz_sessions`.
UUID отличает запуски в одном чате, revision запрещает устаревшую запись.
Завершённую сессию нельзя возобновить сохранением старого снимка. Фото-сессии
и игры других чатов не затрагиваются.

Перед отправкой вопроса записывается фаза `sending`. После ответа Telegram
сохраняются poll ID, message ID, правильный индекс после перемешивания,
содержимое вопроса, текущий индекс серии и абсолютный дедлайн UTC. Подтверждение
записи ожидается до установки jobs. Пустой/неуспешный ответ БД не заменяется JSON.

Ответ блокирует строку сессии и проверяет UUID, наличие опроса, активный статус
и дедлайн до начисления. Журнал ответов, профиль и достижения остаются одной
транзакцией. Завершение использует ту же блокировку; уже начатое начисление
завершается перед закрытием. Очки сессии при восстановлении и показе итогов
собираются из `poll_answers`, а не из потенциально устаревшего счёта в памяти.
Правила сессионного счёта не изменены: +1 / −0,5; бонусы общего рейтинга отдельно.

## Перезапуск

| Сохранённое состояние | Действие |
| --- | --- |
| `ready` | Запланировать ещё не отправленный вопрос |
| `active` | Восстановить опросы и jobs по исходным дедлайнам, без повторной отправки этих опросов |
| `sending` или `is_stopping` | Пометить interrupted; известные сообщения поставить на очистку, очки сохранить |
| completed / stopped / interrupted | Не восстанавливать игру |
| Старый runtime/legacy снимок без poll ID и дедлайнов | Пометить interrupted, сохранить содержимое записи |

Просроченные таймеры обрабатываются после запуска. Старый таймер или ответ
к предыдущему опросу не продвигают более новый вопрос. UUID и ожидаемый индекс
повторно проверяются после ожидания блокировки отправки. Остановка ждёт
подтверждения уже отправляемого опроса. Поддерживается **один процесс бота**;
это не распределённая система исполнения jobs.

PTB восстанавливает меню из отдельного `*.postgres-ui.pickle`, без `bot_data`.
Старый pickle не загружается поверх сервисов и игрового состояния PostgreSQL.
На первом переходе в PG незавершённое меню потребуется открыть заново.

При миграции лучше дать текущим JSON-играм закончиться перед остановкой writers.
Старый снимок без данных опросов нельзя достоверно продолжить; прерывание такой
игры не удаляет накопленные рейтинги и импортированные профили.

## Очередь удаления

`CleanupQueue` использует `message_cleanup_queue` (модель `MessageCleanupItem`):
адресные enqueue / acknowledge / defer вместо замены всей таблицы снимком.
Ключ — chat ID + message ID. Повторная постановка не сдвигает первоначальный
дедлайн. Подтверждение создаёт `done`-запись даже до запоздалой постановки:
старый enqueue не возвращает удалённое сообщение в работу.

Закрытие классической или фото-сессии и постановка её **известных** message IDs
в очередь происходят одной транзакцией. Для них используется задержка 180 секунд.
Новые результаты, отправленные после закрытия, ставятся отдельной ожидаемой
командой. Для обычных служебных сообщений сохраняется переданная задержка,
по умолчанию — 120 секунд. Legacy timestamps нормализуются при первом чтении.

Worker запускается раз в 15 секунд, до 50 записей за проход. Сетевой сбой оставляет
сообщение pending с повтором через 30 секунд. Ошибка отсутствующего/неудаляемого
сообщения считается терминальной; `Chat not found` не выбрасывает запись.
`RetryAfter` сохраняет общую паузу **очереди очистки** в `SystemState`, включая
следующий проход и перезапуск. Это не общий rate limiter всех отправок бота.

Worker читает текущую настройку `auto_delete_bot_messages` для каждого чата
на проход. При отключении ничего не удаляет и откладывает записи на пять минут;
после включения они снова могут быть обработаны. При недоступной БД удаление
не начинается. `done`-записи пока не очищаются автоматически: их удаление без
правила хранения позволило бы старым командам снова поставить сообщения.

## Границы гарантий

- Между Telegram и БД нет общей транзакции. Если Telegram принял вопрос, но
  подтверждение потерялось, автоматический повтор sendPoll в PG отключён.
  Неизвестный результат прерывает игру вместо потенциального дубликата.
- Выдача итогов и пояснений пока не имеет transactional outbox. Они могут не
  дойти или повториться при сетевой неопределённости; начисленные очки остаются
  в БД. Нельзя гарантировать очистку сообщения, ID которого не удалось сохранить.
- Старый синхронный `BotState.add_message_for_deletion` ставит обычные служебные
  сообщения фоновой командой. Авария до её commit может потерять такую заявку;
  закрытие игр и их известные ID этим путём не сохраняются.
- Отмена голосования не пересчитывает исторические баллы. Поздно обработанный
  ответ после сохранённого дедлайна не засчитывается, даже если update задержался.
- Ни надёжная доставка Telegram, ни live-проверка в тестовом чате этим набором
  автоматических проверок не подтверждаются. Production-перенос требует отдельной
  приёмки и свежего серверного snapshot, не копирования локальной тестовой БД.

## Проверки

`tests/test_classic_recovery.py`, `tests/test_durable_cleanup.py` и
`tests/test_telegram_persistence.py`: рестарт, дедлайны, конкурирующие таймеры,
ответ против закрытия, откат закрытия вместе с очередью, устаревший UUID,
восстановление счёта из журнала, настройки удаления, сетевые ошибки, пауза
очереди, предел batch и отделение pickle от БД. Telegram заменён заглушками,
PostgreSQL — настоящая отдельная тестовая БД.
