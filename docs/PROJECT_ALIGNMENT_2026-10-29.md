### 2.3. Экономика и формулы текущего среза

- Качество: `grade(cov, ov)`, затем `quality_full(score) = 850 + 400 * score / 1000` (850–1250).
- Автопилот `rules=3`: 900. Время: бонус над автопилотом целый до 2,5× A, тает до 0 к 6× A.
- Урон: `condition` 100; удар −3, ремонт 15 монет/удар, штраф качества 4 ‰ за пункт состояния. При 0% — заезд закрывается автопилотом с 90%.
- Культивация: время роста `base * (1950 − q_cult) / 1000`; при 1250 — 700 (до −30%).
- Опрыскивание: `q_spray` хранится в посадке; прибавка `1000 + (q_spray − 850) * 1000 / 2000` ‰, максимум 1200 (+20%). Урожай: `base * q_sow * q_harvest * q_spray / 10^9`.
- Бак: 24 л на 1 га в единицах отображения; внутри — 48 половинных единиц на 1 га. Одна клетка — 2 единицы, ветровой снос — 1, повтор — 1. Заправка/выгрузка — 4 чанка; бункер — `ceil(cap / 4)`.
- Ветер: ±1, детерминированно из seed, сносит распыл на соседнюю клетку.
- Опрыскивание доступно только на созревшем поле, один раз; повторное отклоняется.

Профиль — **общая платформенная возможность Account**, а не экран одной игры. Все игры и каналы должны читать/писать одни и те же Account-настройки; игра не должна заводить отдельный профиль.

| **Имя и профиль** | `display_name`, ручное имя гостя, импорт Telegram-имени только при «Гость», отдельное имя фермы, скрытие рейтинга, фильтр placeholder-имён | Живая приёмка Telegram/гостя; не смешивать имя Account и имя фермы |

| **Рейтинги** | global/room/chat/friends/farm/alchemy; period all/month/week; скрытый профиль; без Telegram/account ID | Живая/клиентская приёмка; `rating_hidden` и placeholder-фильтры |

Профильные выводы:

- **Профиль связан с каждым game scope**: Classic/Photo/Mafia/Alchemy, ферма и её мини-игры используют один Account; нельзя делать «профиль фермы» отдельно.
- **Address form и contrast** — Account-level, но их тексты/экраны живут в адаптерах; нужна матрица всех мест, иначе появятся гибриды «собрал(а)».
- **Рейтинги и приватность** — общий контракт: строки без идентификаторов, скрытый игрок видит своё место, но не попадает в публичные срезы.
- **Друзья/соседи/комнаты** — самая опасная зона: без явного контракта адаптеры могут автоматически «подружить» игроков при входе в комнату или приглашении на ферму.

## 4. Глубокий анализ несогласованности

### 4.1. Корневая причина

В проекте нет **единой модели поставки**:

- нет разделения Core Release / Farm Product Track / Night City Product Track;
- нет статус-модели с evidence (dev/sandbox/accepted/done/blocked);
- task-доки, реестр и STATUS обновляются вручную и расходятся;
- часть канонических документов не в git;
- экономические константы дублируются в доках и коде;
- несколько worktree/веток ведут параллельные срезы без общего плана.

Это не обязательно ошибки реализации; это **долг согласованности**. Он приводит к неверным приоритетам и повторной работе.

### 4.3. Что это означает для приоритетов

- **Core Release** (платформа, вход, Room/Game, Classic/Photo/Mafia/Alchemy, Telegram/браузер) и **Farm Product Track** — разные программы. Если ферма не входит в первый релиз, её `.bulk-plan`-тест не должен красить Core gate; если входит — это нужно явно записать и принять farm gate.
- **Night City** нельзя планировать одной строкой: async Mafia/NC-OPEN — ближе к Core, weekly detective — будущий продукт.
- **«Реализовано» не равно «принято»**: без evidence-статусов любой отчёт о готовности субъективен.
- **Экономика** должна иметь один источник; иначе каждая новая farm-фича будет считать по своим числам.

## 5. Целевая модель: единая система в рамках scope

### 5.1. Три программы и общие контракты

```
Core Release
  Account / Room / Game / invitations / identity
  Classic / Photo / Async Mafia / Alchemy
  Telegram + browser, PostgreSQL, migrations, release gate
        │
        ├── Farm Product Track (account-linked, собственный farm state)
        │     поля, культуры, сад, удобрения, текстиль, плантации, редкий урожай
        │     отдельная owner-приёмка; не блокирует Core без решения
        │
        └── Night City Product Track
              async Mafia / open rooms (сейчас)
              weekly detective / cases / art (после чисел и формата)
```

Общие контракты между программами:

- **Account** — канонический игрок; Telegram/HTTP — адаптеры.
- **Room/Game** — только там, где это игры; ферма не обязана быть Room.
- **Relationships** — вход в комнату, друг аккаунта, сосед фермы — разные сущности; никаких неявных превращений.
- **Notifications** — общий outbox/доставка, игровые последствия однократны.
- **UI shell/tokens** — общие токены и правила; игровые экраны имеют общий контракт header/close/menu.
- **Evidence** — тест/живой сценарий/миграция/sandbox URL; без evidence нет accepted.

### 5.2. Статус-модель

Предлагаемые статусы task-документа:

| Статус | Значение | Минимальное evidence |
|---|---|---|
| `proposed` | идея/дизайн | scope и открытые вопросы |
| `approved` | scope и решения владельца приняты | ссылка на решение |
| `queued` | можно брать, но есть порядок | dependencies |
| `dev` | код в dev-копии | diff/тесты |
| `sandbox` | выложено в песочницу | URL/ассеты/миграция |
| `accepted` | владелец/тестировщик принял | сценарий/скриншоты/подпись |
| `done` | выпущено/закрыто | changelog/release |
| `blocked` | нельзя продолжать | причина/кто решает |
| `rejected` | отклонено | причина |
| `superseded` | заменено | ссылка на замену |
| `rehearsed` | репетиция runbook | дата/результат |

Текущие слова «реализовано», «проверено», «не закоммичено» нужно заменить этими статусами или явно маппить в них.

### 5.3. Task-метаданные и реестр

Предлагаемый frontmatter:

```yaml
id: FARM_FIELD
domain: farm
scope: farm
status: sandbox
owner: WeLizard
blocked_by: []
depends_on: [FARM_ECONOMY]
last_verified: 2026-10-29
evidence:
  - python -m pytest tests/test_farm_fields_r9.py -q
  - sandbox: https://quiz.mr-lizard.ru
release_slice: field-2b2c
```

Правила:

- `docs/tasks/README.md` — индекс, генерируемый из frontmatter или проверяемый скриптом; не ручная таблица «кто когда».
