- **Создан:** 2026-10-15

- **Файлы формата:** [`night_city/case.schema.json`](night_city/case.schema.json) — машиночитаемая схема; [`night_city/example_case.json`](night_city/example_case.json) — учебный пример

> **Статус 2026-10-15: сюжеты и заказы приостановлены** (решение Ильи: «рано
> сюжет прописывать» — сначала формат и движок). Пробный заказ №001 выполнен

>

> (этап 2 плана). Для примера написан одноразовый прототип проверок (§4), он
> **не** является валидатором.

## 1. Принципы

1. **Одно дело — один JSON-объект** по схеме `night-city-case/1`. Лишних полей нет
   (`additionalProperties: false`), все ссылки — по `id` внутри файла.
2. **Модель не решает игру.** Она описывает мир, факты, улики, диалоги и несколько
   вариантов разгадки. Кто виновен в конкретной партии, выбирает сервер при старте.
3. **Правда — таблица.** Каждый факт помечен, в каких вариантах он истинен. Из этой
   таблицы валидатор выводит противоречия, достижимость и утечки.
4. **Модели не доверяем.** Любой результат — черновик; публикует человек после
   автоматической приёмки (§6).
5. **Разнообразие задаётся заказом**, а не надеждой: каждому заказу выдаются свои
   «зёрна разнообразия» (§5.2).

## 2. Схема

Файл: [`night_city/case.schema.json`](night_city/case.schema.json) (JSON Schema 2020-12).
Проверка схемой: любой стандартный валидатор JSON Schema. Схема проверяет форму
(типы, перечисления, длины, обязательные поля, формат `id`: `^[a-z][a-z0-9_]{1,31}$`),
но **не** смысл. Смысл проверяет валидатор (V2–V11, дизайн §18).

## 3. Описание полей

**Корень:** `schema`, `meta`, `setting`, `locations`, `characters`, `facts`,
`evidence`, `dialogues`, `variants`, `events` (необязательно), `endings`.

**Имена и ссылки на героев** *(по замечанию Ильи 2026-10-15)*. Имена героев —
**входные данные партии**, а не часть дела: игроки играют под своими именами, а
героев, которых ведёт игра (NPC), сервер при старте называет **случайными**
именами из пула эпохи `meta.npc_name_era` (уникально, не совпадая с именами
игроков; выбор записывается в состояние партии, поэтому не меняется при
перезапуске). Поэтому в тексте дела **нет ни одного имени человека**. Ссылки:

| Запись | Что подставляется | Правила |
| --- | --- | --- |
| `{c:id}` | имя героя за столом (имя игрока или имя NPC) | **только именительный падеж**: имена не склоняются; глаголы согласуются с `gender` героя |
| `{t:id}` | роль героя (`title`) | именительный |
| `{t:id\|gen}`, `\|dat`, `\|acc`, `\|ins`, `\|prep` | форма роли из `title_forms` | для косвенных падежей используйте роль, а не имя |

Иные фигурные скобки в текстах запрещены (схема это проверяет). Предложение не
начинают с `{t:…}` (формы написаны строчными). Неразрешённые вопросы — в дизайне,
вопросы 25–26 (род героя и игрока, имена из пула).

Что **обязательно** для боевого дела (схема допускает меньше, ради учебного
примера; проверяет валидатор):

- ≥12 героев с `can_be_player=true` и 1–3 NPC-only; ≥6 `core`;
- 6–8 мест, граф связный;
- 3–4 варианта разгадки с **разными** виновными;
- на каждый вариант 4–6 ключевых улик, `min_key` 3, не менее двух независимых путей;
- ≥2 ложных следа на вариант, у каждого есть опровержение;
- ключевые улики **не** через диалог (героя может играть человек, и NPC-диалога тогда нет);
- составы 4/5/8/12 перечислены в `compositions` для каждого варианта.

## 4. Пример

[`night_city/example_case.json`](night_city/example_case.json) — учебное дело
«Тихая пристань»: 6 героев, 5 мест, 12 фактов, 11 улик, 2 варианта, 6 финалов.
Оно **намеренно мало**: поддерживает 4–5 игроков, чтобы показать все поля.
Боевое дело обязано поддерживать 4/5/8/12 (см. §3).

Что в примере показано:
- один и тот же «Журнал причала» существует в разных вариантах в разном виде
  (`e_pier_left` и `e_pier_stay`);
- `e_debt` — ключ в одном варианте и ложный след в другом, его опровергает `e_pier_stay`;
- свидетель-NPC (`e_pavel_word`) лжёт в варианте `v_gleb`: факт `f_pavel_saw_nothing`
  истинен только в `v_igor`;
- ложный след на Марту (`e_vera_word`) опровергается запиской (`e_key_receipt`);
- цепочка `e_lock → e_forged`, `e_boat_photo → e_pavel_envelope`;
- событие `ev_storm` закрывает пристань на окна 5–6.

Прототип проверок (одноразовый скрипт, в репозиторий не добавлен) прогнан на примере:
схема + целостность ссылок + алиби (V2) + различимость вариантов (V3) +
достижимость ключевых улик при NPC и при всех людях (V4) + опровержение ложных
следов (V5) + достаточность играбельных героев (V7) — **ошибок нет**.
Это проверка примера, а не готовность валидатора.

## 5. Как заказать дело у внешней модели

### 5.1 Что нужно для заказа

Заказ собирается из трёх вставок и параметров:

1. **Бриф** (§5.3) с подставленными параметрами заказа (§5.2).
2. **Схема** — содержимое `case.schema.json`.
3. **Пример** — содержимое `example_case.json`.

Модели, у которых контекст маленький, получают бриф + схему, а пример — по запросу.
Внешняя модель не получает ни исходников, ни данных игроков.

Каналы доставки заказа — в §5.5 (веб-чат модели, роутер бесплатных моделей,
прямой API). Сам бриф от канала не зависит.

### 5.2 Параметры заказа (подставляются в бриф)

| Параметр | Что значит | Пример |
| --- | --- | --- |
| `{{ORDER_ID}}` | номер заказа (для учёта) | `order-2026-10-001` |
| `{{GENRE}}` | `noir` / `classic` / `mystic` | `classic` |
| `{{CASE_ID}}` | `id` дела (snake_case) | `winter_manor` |
| `{{EPOCH_AND_PLACE}}` | время и место | «зима 1930-х, усадьба на озере» |
| `{{CRIME_TYPE}}` | вид происшествия | «исчезновение завещания» |
| `{{MOTIVE_TYPES}}` | типы мотивов по вариантам (разные) | «деньги, ревность, шантаж» |
| `{{TWIST}}` | поворот | «свидетель сам виновен в другом» |
| `{{TONE}}` | тон | «камерный, без крови» |
| `{{VARIANTS}}` | число вариантов 3–4 | `3` |
| `{{SUPERNATURAL}}` | `false` или правила | `false` |
| `{{BANNED_TITLES}}` | занятые названия | список |

**Зёрна разнообразия** (`EPOCH_AND_PLACE`, `CRIME_TYPE`, `MOTIVE_TYPES`, `TWIST`, `TONE`)
берутся из каталога так, чтобы каждая новая комбинация отличалась от уже принятых
дел; ведётся матрица покрытия «место × мотив × поворот» (§7, риск R5). Каталог зёрен
создаётся на этапе 2; сейчас он не существует.

### 5.3 Готовый бриф

Текст ниже вставляется в запрос целиком (с подстановкой `{{…}}`). Схема и пример
прикладываются следом под заголовками `СХЕМА:` и `ПРИМЕР:`.

````text
Ты — автор детективных сюжетов для командной игры «Ночной город»: недельное
расследование на 4–12 человек, ходы два раза в сутки, у каждого игрока свой
герой, тайна и цель. Твоя задача — написать ОДНО дело в виде ОДНОГО JSON-объекта.

ФОРМАТ ОТВЕТА
- Ответ — только JSON-объект, без пояснений, без Markdown и без ``` до и после.
- Объект строго соответствует JSON Schema «night-city-case/1» (приложена ниже).
  Лишних полей быть не должно. Все id — snake_case: ^[a-z][a-z0-9_]{1,31}$.
- Все ссылки (location, character, fact, evidence, variant, dialogue) должны
  указывать на существующие id в этом же объекте.
- Язык текста — русский. Никаких иероглифов, латиницы (кроме id) и эмодзи.
- В текстах запрещены HTML, Markdown, ссылки и обращения к ИИ/читателю.
- Все длины — в пределах схемы.

ПАРАМЕТРЫ ЗАКАЗА {{ORDER_ID}}
- id дела: {{CASE_ID}}; жанр: {{GENRE}}; время и место: {{EPOCH_AND_PLACE}}.
- Происшествие: {{CRIME_TYPE}}. Тон: {{TONE}}. Поворот: {{TWIST}}.
- Вариантов разгадки: {{VARIANTS}}; мотивы по вариантам — разные: {{MOTIVE_TYPES}}.
- Сверхъестественное: {{SUPERNATURAL}}. Если false — ни одна улика не должна
  объясняться только сверхъестественным. Если true — опиши правила в
  meta.supernatural.rules и не противоречь им.
- Названия дела, которые НЕЛЬЗЯ использовать: {{BANNED_TITLES}}.
- meta.author = {"kind":"model","name":"<твоё название>"}; meta.version = 1.
- meta.npc_name_era подбери по времени действия: ru_modern, ru_1900_1930,
  ru_1930_1960 или neutral.

ИМЕНА И ССЫЛКИ НА ГЕРОЕВ (ВАЖНО)
- У героев НЕТ собственных имён. Игроки играют под своими именами, а героев,
  которых ведёт игра, сервер называет случайными именами при старте партии.
  Поэтому НИКОГДА не пиши имён людей в текстах (ни имён, ни фамилий, ни отчеств).
- У каждого героя есть title (роль или должность, например «Экономка»),
  title_forms (gen, dat, acc, ins, prep — формы этого title строчными буквами)
  и gender: "f" или "m".
- Чтобы сослаться на героя в любом тексте (bio, факты, улики, диалоги, мотивы,
  финалы), пиши:
  {c:id} — имя героя; только в именительном падеже, имена НЕ склоняются;
  {t:id} — его роль в именительном;
  {t:id|gen}, {t:id|dat}, {t:id|acc}, {t:id|ins}, {t:id|prep} — роль в падеже.
  Для косвенных падежей используй роль, а не имя («у {t:vera|gen}», «{t:gleb|dat}»).
  Глаголы в прошедшем времени согласуй с gender героя.
- Предложение не начинай с {t:...}. Никаких других фигурных скобок в текстах.
- Названия мест допустимы, имена людей — нет.

ОБЪЁМ И СОСТАВ
- Героев: не меньше 14: минимум 12 с can_be_player=true и 1–3 только NPC
  (can_be_player=false). Минимум 6 героев tier="core". Фракции по умолчанию:
  минимум 3 investigation, минимум 3 independent; shadow по умолчанию не нужны —
  виновных определяет вариант.
- Мест: 6–8; граф связный, связи симметричны.
- Дней 7, окон 14 (окно 1 — первое утро). Все окна в полях — числа 1..14.
- Фактов: 30–60. Улик: 35–60. Диалоговых узлов: 20–60. Событий: 3–8.
- Вариантов разгадки: {{VARIANTS}}, виновные РАЗНЫЕ. compositions каждого варианта
  включает 4, 5, 8 и 12 (если вариант невозможен на малом составе — не включай его).
- Финалов: по одному на accusation_proven для каждого варианта, а также
  accusation_unproven, shadow_framed, evidence_destroyed, no_investigators,
  final_hearing, frozen.

КАК УСТРОЕНА ПРАВДА (ВАЖНО)
- Каждый факт имеет true_in: "all" (истинен во всех вариантах), "none" (ложен во
  всех вариантах — только для ложных утверждений свидетелей) или список вариантов,
  где он ИСТИНЕН. Пустой список [] недопустим.
  Факты, зависящие от виновного, истинны только в части вариантов.
- Улика раскрывает один факт (поле fact). Физическая улика (physical/document/
  trace) существует (exists_in) ТОЛЬКО в вариантах, где её факт истинен.
- Показание (testimony) может быть ложью: его факт истинен не во всех вариантах;
  там, где факт ложен, свидетель лжёт или ошибается.
- Для фактов «герой был в месте X» заполняй at {character, location, window}
  (окно 0 — ночь до начала дела). В одном варианте один герой не может быть в
  двух местах в одном окне.
- Для каждого варианта:
  * 4–6 ключевых улик (key_evidence), min_key = 3;
  * не меньше двух независимых цепочек, ведущих к ключевым уликам;
  * ключевые улики получаются осмотром (found.via="examine"), НЕ через диалог:
    героя из диалога может играть человек, тогда NPC-диалога не будет;
  * цепочка requires не длиннее двух звеньев;
  * НИ ОДНА ключевая улика не должна быть доступна раньше окна 3;
  * не меньше двух ложных следов (misleads_toward) с реально существующим
    опровержением (debunked_by);
  * улики, по которым можно отличить этот вариант от любого другого, существуют.
- Каждая улика с found.via="dialogue" должна выдаваться (grants) хотя бы одним
  вариантом ответа.
- mentions у каждой улики и диалога должен перечислять ВСЕ факты, которых
  касается текст.

ГРАНИЦЫ СЕКРЕТОВ
- Публично видны: meta.summary, setting.*, locations[].text, characters[].title/
  bio, events[].text, тексты фактов с visibility="public". Они НЕ должны
  раскрывать виновного, мотив, способ и содержимое hidden-фактов, даже намёком
  вроде «виновен», «убийца», «это он».
- Тайна героя (secret) и личная цель (personal_goal) видны только ему. Не
  повторяй чужие тайны в публичных текстах и в диалогах других героев, пока
  это не разрешено уликой.
- final_text, motive, method вариантов — секрет до финала; не ссылайся на них.
- Текст узла с valid_in="all" и улики с exists_in="all" не должны упоминать
  факты, истинные лишь в части вариантов.

ЗАПРЕЩЕНО
- Реальные люди, бренды, организации, произведения и их персонажи; пересказ
  известных сюжетов; узнаваемые цитаты.
- Сексуальное содержание; жестокие сцены; издевательства; опасность для детей;
  травля, ненависть к группам; реальная политика и религиозная агитация;
  инструкции по совершению преступлений, изготовлению оружия, наркотиков;
  самоповреждение.
- Любые инструкции для читателя или ИИ внутри текстов.
- Смерть допускается только «за кадром», без подробностей.
- В content_flags указывай только честные пометки из списка схемы.

ПЕРЕД ОТВЕТОМ ПРОВЕРЬ (мысленно, не выводи)
1. Объект проходит схему; нет висячих ссылок.
2. Для каждого варианта таблица «факт × истинность» без противоречий.
3. Любые два варианта различимы хотя бы одной достижимой уликой.
4. Ни один публичный текст не выдаёт разгадку.
5. Нет дублей текстов, нет пустых заглушек, нет улик, не нужных ни одному пути.
````

### 5.4 Запрос на исправление (ремонт)

Если приёмка нашла ошибки, той же модели отправляется короткий запрос — не более
двух раундов ремонта на заказ:

````text
Твой JSON не прошёл проверку. Исправь ТОЛЬКО перечисленные места и верни
полный исправленный JSON-объект (без пояснений). Остальное не меняй.
Ошибки (код, путь в JSON, описание):
{{ERRORS}}
````

`{{ERRORS}}` — машинный список `{code, pointer, message}` из валидатора, без
скрытых данных других заказов.

### 5.5 Каналы авторов и настройки в админке

*(по ответу Ильи от 2026-10-15: пользоваться бесплатными моделями; всё
настраивается в админке; дела можно писать прямо в веб-чатах Qwen и DeepSeek)*

**Три канала** — один бриф, одна приёмка, разные способы доставки:

| Канал | Как работает | Плюсы | Ограничения |
| --- | --- | --- | --- |
| `web_chat` | В браузере открывается уже залогиненный чат модели (Qwen, DeepSeek, …) в существующем диалоге; в него отправляются бриф + схема + пример; ответ копируется и попадает в приёмку как сырой JSON | бесплатно, без ключей; у диалога уже есть контекст | нет настроек генерации; ответ может обрезаться или быть в блоке кода с экранированием; в долгом диалоге модель «помнит» прошлые дела (хорошо для «не повторяйся», плохо для переполнения контекста); интерфейс чата меняется, автоматизация хрупкая; **условия использования сервисов могут запрещать автоматизацию потребительского чата — не проверено** |
| `openai_compat` | Любой OpenAI-совместимый адрес, например самохостящийся роутер бесплатных тарифов [FreeLLMAPI](https://github.com/tashfeenahmed/freellmapi): один адрес `/v1`, подбор модели, переключение при лимитах 429/5xx, ключи провайдеров хранятся у вас локально | автоматический ремонт и повтор; учёт лимитов | по описанию автора проект — для личных опытов, не для продакшена; набор провайдеров меняется; лимиты бесплатных тарифов малы; качество модели заранее неизвестно |
| `provider_api` | Прямой API конкретного провайдера по ключу | предсказуемость | ключи и условия; не нужен, пока хватает первых двух |

Источники сведений о FreeLLMAPI: [репозиторий](https://github.com/tashfeenahmed/freellmapi),
[обзор Better Stack](https://betterstack.com/community/guides/ai/freellmapi/);
на самом проекте у нас ничего не проверялось и не запускалось.

**Настройки «Авторы дел» в админке** (редактируются владельцем, версионируются,

не в `.env` как единственном месте):

| Настройка | Смысл |
| --- | --- |
| Список авторов | для каждого: имя, канал, адрес/ссылка диалога, ID модели, «включён», приоритет |
| Правило выбора | по очереди / по приоритету / по «карточке модели» (качество приёмки) |

| Шаблон брифа | текущая версия и история; подстановки §5.2 |
| Каталог «зёрен разнообразия» | редактируемые списки времени/места/мотива/поворота/тона |
| Пороги проверок | таблица §7.2 с допустимыми диапазонами; изменение сохраняет версию, вернуться можно |
| Словари содержимого и запреты | редактируемые списки (R7, R8) с историей |
| Корпус и повторы | какие дела считаются «уже принятыми» |
| Режим приёмки | какие шаги блокирующие; ИИ-ревью вторым автором — вкл./выкл. |

Внимание: существующие настройки админского ИИ сейчас берутся из переменных
окружения (`MQB_ADMIN_AI_ENABLED`, ключи и модели провайдеров:
[`modules/admin_ai.py:18-24`](../../modules/admin_ai.py)); редактируемого в админке
зашифрованного хранилища секретов я не нашла — это **предположение**, проверить
на этапе 6 (не искала в `storage/settings.py` и системных состояниях).

**Порядок заказа через `web_chat` (когда придёт время):**
0. Браузер — Chrome владельца (расширение Claude in Chrome), где он уже залогинен;
   встроенный браузер приложения не используется, пока там нет входа. Кто
   авторизуется — владелец; пароли агенту не передаются.
1. Владелец залогинен в нужном чате (учётные данные агенту не передаются и не вводятся).
2. Агент формирует бриф из шаблона и параметров заказа, показывает владельцу итоговый текст.
3. Отправка в чат внешнего сервиса — по явному «да» владельца (на каждый заказ).
4. Ответ сохраняется как сырой, дальше обычная приёмка (§6).

Бесплатные модели повышают риски R10, R12, R14 (качество и язык нестабильны) и
R15 (условия использования), поэтому «карточка модели» и ремонт — штатная часть
процесса, а не исключение. Бесплатный роутер подходит для **черновиков дел**;
для текста, который игрок видит во время партии, игра всегда имеет авторский
текст и не зависит от доступности модели (дизайн §16).

4. Практика заказа: длинный бриф лучше слать вложением или короче; DeepSeek в
   момент теста недоступен; частями («дальше») Qwen работает, 3 части заняли

## 6. Шаги приёмки

Результат каждого шага: `pass` / `warn` / `fail`. `fail` возвращает на ремонт (§5.4)
или отклоняет заказ.

| № | Шаг | Что делается | Блокирует |
| --- | --- | --- | --- |
| 0 | Приём | Сырой ответ сохраняется как есть; к нему прикладывается происхождение: модель и версия, дата, `ORDER_ID`, хеш брифа, параметры. В игру ничего не попадает | — |
| 1 | Разбор | Снять ограждения ```, строгий JSON (дублирующие ключи, NaN, BOM — ошибка); размер ≤ 512 КБ; санитайзер строк (§7, R8, R10) | да |
| 2 | **Валидатор** V1–V11 (дизайн §18) | схема, целостность, непротиворечивость, различимость, достижимость, ложные следы, границы секретов, составы 4/5/8/12, финалы, мистика, доступность | V1–V10 блокируют |
| 3 | **Противоречия и утечки** | дополнительные проверки U1–U8 (§7, R1, R6) + необязательный разбор второй моделью: ей даётся готовый JSON и просьба найти противоречия; выводы — подсказки, не вердикт | U-проверки блокируют; ИИ-ревью — нет |
| 4 | **Пробный прогон** | боты на каждом составе и варианте: «идеальный», «ленивый», «наивный по числу подозрений», «случайный», «Тень»; затем одиночное прохождение человеком по каждому варианту в предпросмотре (читает все тексты, отмечает затыки и спойлеры) | пороги метрик (§7.2) и чек-лист человека |
| 5 | Ревью человека | содержание, соответствие `content_flags`, повтор с корпусом, список иллюстраций, решение: публиковать / в ремонт / отклонить | да |

Публикует только человек (дизайн §8): кнопка недоступна, пока шаги 1–4 не `pass`
(допустимы `warn` с пометкой ревьюера).

## 7. Риски внешних авторов и автоматические ловушки

Условные имена проверок: **V** — из дизайна §18, **U** — дополнительные из этого документа.

| № | Риск | Как проявится | Что ловит автоматически | Остаётся человеку |
| --- | --- | --- | --- | --- |
| R1 | **Противоречивые улики** | один герой в двух местах; «надёжная» улика ложна в варианте, где она существует; факты друг другу противоречат; событие закрывает место, где единственный ключ | V2: по `at` и расписаниям строится положение героя в каждом окне варианта, конфликт = ошибка; U1: `reliability=solid` ⇒ факт истинен во **всех** вариантах из `exists_in`; U2: физическая улика существует только там, где факт истинен; U3: улика с окном `found.windows`, целиком попавшим под `lock_location`, недостижима; расписание не ставит героя в закрытое место | тонкие смысловые противоречия текста («был ночью» против «шёл дождь»): помощь — ИИ-ревью второй моделью, подсказка |
| R2 | **Неразрешимое дело** | ключевая улика недостижима по окнам, цепочкам, графу мест или требует диалога с героем, которого играет человек | V4: симуляция «идеального следователя» по графу, окнам, `requires`, блокировкам и диалогам — для каждого варианта и состава, включая случай «все диалоговые герои — люди»; ключ через диалог = ошибка; ёмкость хода: стоимость кратчайшего пути ≤ 35 % суммарных ходов стола при 4 игроках (предложение) | интересно ли это |
| R3 | **Слишком очевидное** | виновный ясен за первые окна; единственная улика всё объясняет; ложных следов нет | U4: самая ранняя достижимая ключевая улика не раньше окна 3; нет одиночной улики с `requires=[]`, раннего окна и `key_for` одного варианта вместе с прямым указанием на виновного; U5: «наивный бот» (выбирает подозреваемого по числу указывающих на него улик) не должен выигрывать > 40 % (предложение) вариантов за ≤ 4 окна; «случайный бот» ≈ 1/число подозреваемых; ложных следов ≥ 2 на вариант | ощущение сложности: решает человек в пробном прохождении |
| R4 | **Слишком запутанное** | нужен длинный путь; улик мало для 4 игроков | V4: длина цепочек ≤ 2; ёмкость (R2); «ленивый бот» должен дойти хотя бы до итогового слушания без падений | |
| R5 | **Повторы между моделями и делами** | одинаковые имена, схожие сюжеты и структура | U6: нормализованный текст → шинглы по 5 слов (MinHash/Jaccard): `summary`, `setting`, `characters[].bio`, `variants[].motive`; Jaccard ≥ 0,35 — предупреждение, ≥ 0,60 — отказ (предложение); совпадение полных имён/названий с корпусом > 3 — предупреждение; **структурный отпечаток**: размеры списков, матрица «вариант × факт» после канонической сортировки, длины путей — хеш и расстояние до корпуса; матрица покрытия «место × мотив × поворот»; зёрна разнообразия в брифе (§5.2) | смысловые повторы при разных словах: сравнение глазами / эмбеддинги (предположение: понадобится локальная модель эмбеддингов, решения нет) |
| R6 | **Утечка разгадки** | публичный текст выдаёт виновного; вариант «просвечивает» через общий текст; тайна героя в чужом диалоге | U7 (вокруг `mentions` и текста): (а) публичные поля (`summary`, `setting`, `locations.text`, `characters.bio/job`, `events.text`, диалоги и улики с `valid_in/exists_in = all`) не упоминают факты, истинные не во всех вариантах; (б) лексический след: содержательные слова скрытых фактов (лемматизация или стемминг) в публичных текстах — пересечение ≥ 0,5 ⇒ подозрение; (в) имя виновного рядом со словами «виновен/убил/украл/преступник» в публичных текстах; (г) факты, упомянутые в тексте по `id`/ключевым словам, но отсутствующие в `mentions`; (д) `secret`/`personal_goal` героя X не цитируются в текстах, видимых другим; (е) `final_text`, `motive`, `method` не достижимы ни через одну проекцию (структурно, тест канарейки); V6 | искусный намёк без общих слов |
| R7 | **Неподходящий контент** | жестокость, сексуальное содержание, дискриминация, реальные люди и бренды, политика, инструкции по преступлениям, нарушение возрастной планки | U8: словари запрещённых тем (корни слов, регулярные выражения) по категориям; сверка с `content_flags`; сигнал при реальных именах/брендах (список публичных персон и брендов — предположение, придётся собрать); необязательная классификация второй моделью — только подсказка | **окончательное решение за человеком** (политика допустимого — вопрос владельцу) |
| R8 | **Внедрение в тексты** | HTML, Markdown, ссылки, «игнорируй прежние инструкции», скрытые символы; позже эти тексты попадут в запрос к ИИ-ведущему | санитайзер: запрет `<`, `>`, `http`, `](`, `` ` ``, управляющих и невидимых символов (ZWJ, RTL и т.п.), эмодзи; список «инъекционных» фраз («игнорируй», «system:», «ты — ИИ»…) ⇒ fail; тексты всегда как данные, не как инструкции | |
| R9 | **Нарушение схемы, висячие ссылки** | модель выдумала id, нарушила длину, добавила поля | схема + V1; ремонт ≤ 2 раундов по машинным ошибкам (§5.4) | |
| R10 | **Язык и качество** | иероглифы (характерно для некоторых моделей), смесь языков, опечатки, нескладный перевод, анахронизмы | доля букв вне кириллицы (кроме `id`) > 0 ⇒ fail для CJK/арабских, предупреждение для латиницы; длины/пустые строки; проверка орфографии — подсказка (предположение: нужна внешняя библиотека, не выбрана) | стиль и анахронизмы |
| R11 | **Плагиат известных сюжетов** | пересказ знаменитого романа или фильма | надёжной автоматической ловушки **нет**; частично — U6 по корпусу известных названий и имён (список придётся завести); подсказка: просьба второй модели «назови узнаваемый источник» | проверка человеком |
| R12 | **Подгонка под валидатор** | бесполезные факты и улики, дубли, заглушки, чтобы выполнить пороги | U9: доля «мёртвых» данных (улики/факты вне любого пути, не упомянутые нигде) > 20 % ⇒ предупреждение; дубли и почти-дубли текстов (Jaccard ≥ 0,8) ⇒ fail; минимальная длина текстов | |
| R13 | **Перекос по составам** | на 4 игроках нет следователей, виновный NPC и играть не за что; на 12 не хватает ролей | V7: для каждого состава раздача возможна: у каждого человека есть и смысл (личная цель или способность), и путь к уликам; фракции нигде не пусты, либо противник — NPC по правилам дизайна §5 | |
| R14 | **Дрейф качества между моделями** | одна модель стабильно ломает схему, другая — повторяется | «карточка модели»: доля заказов, прошедших каждый шаг приёмки, число раундов ремонта, метрики R3/R5; слепая оценка владельца; модели с плохой карточкой не получают новых заказов | |
| R15 | **Права и условия использования** | условия модели ограничивают использование её выводов или автоматизацию веб-чата; бесплатные тарифы могут использовать присланное для обучения; различная юрисдикция | происхождение хранится (§6, шаг 0); в бриф не попадают данные игроков | **не проверено**: условия использования выводов и автоматизации чатов Qwen/DeepSeek и других моделей не изучались — проверить до первого заказа |
| R16 | **Стоимость и конфиденциальность** | расход на заказы и ремонты; в бриф попали внутренние данные | в бриф попадают только параметры заказа и публичная схема; лимит раундов ремонта; учёт расходов по `ORDER_ID` | кто платит и где ключи — вопрос владельцу |

### 7.1 Дополнительные проверки (U)

| Код | Проверка |
| --- | --- |
| U1 | `reliability=solid` ⇒ факт истинен во всех вариантах, где улика существует |
| U2 | Не-показание существует только там, где факт истинен |
| U3 | Окна `found` не целиком под `lock_location`; расписания не ведут в закрытое место |
| U4 | Ранняя ключевая улика: окно ≥ 3 |
| U5 | Наивный и случайный боты не выигрывают чаще порога |
| U6 | Сходство с корпусом (шинглы, структурный отпечаток) |
| U7 | Утечки (R6, пункты а–е) |
| U8 | Недопустимое содержимое по словарям и `content_flags` |
| U9 | «Мёртвые» данные и дубли |

### 7.2 Пороги метрик (предложения, подбираются на первых делах)

| Метрика | Порог |
| --- | --- |
| Ранняя ключевая улика | не раньше окна 3 |
| Кратчайший путь, доля ёмкости при 4 игроках | ≤ 35 % |
| Наивный бот, вариантов за ≤ 4 окна | ≤ 40 % |
| Ложных следов на вариант | ≥ 2, каждый с опровержением |
| Независимых путей к `min_key` | ≥ 2 |
| Мёртвые данные | ≤ 20 % |
| Jaccard сходства с корпусом | предупреждение 0,35; отказ 0,60 |
| Раундов ремонта | ≤ 2 |

### 7.3 Что не ловится автоматически

Смысловые намёки на разгадку без общих слов; интересность и тон; плагиат при
смене деталей; тонкие внутренние противоречия художественного текста; культурные
и этические оттенки; права на текст. Для них — шаг 5 (человек) и предпросмотр
«сыграть за роль».
