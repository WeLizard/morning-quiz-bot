# Разработка Morning Quiz

Это актуальный процесс для dev-копии. Целевая архитектура и текущая готовность
различаются: правила ниже определяют направление изменений, а не утверждают,
что самостоятельное приложение уже реализовано.

## Начало задачи

1. Установи корень, ветку и исходный diff. Уточни dev/production по
   [AGENTS.md](../../AGENTS.md). Сохрани чужие изменения.
2. Определи наблюдаемое поведение и критерии приёмки. Для локального исправления
   достаточно краткого описания; для нового режима, миграции или архитектуры
   обнови задачу в `docs/tasks/` и при необходимости ADR.
3. Выбери релевантный проектный skill. Читай только нужные исходники и документы.
4. Реализуй законченный пользовательский сценарий, проверь его, обнови сведения
   о готовности. Не добавляй новый слой только ради структуры каталогов.

При конфликте старого описания с кодом зафиксируй расхождение. Число тестов,
проценты готовности и дата старого smoke сами по себе не определяют текущий статус.

## Направление архитектуры

```text
Браузер / Telegram Mini App / Telegram Bot
                  ↓
        общие application commands
                  ↓
  доменные правила режимов + PostgreSQL
                  ↑
   независимый worker дедлайнов и событий
                  ↓
       outbox → доставщики уведомлений
```

Аккаунт приложения может иметь Telegram identity. Комната может быть связана
с Telegram chat. Собственные идентификаторы аккаунта/комнаты/партии не должны
требовать наличия Telegram ID. Связывание идентичностей подтверждает владение;
одинаковые имена или адреса не являются основанием объединять аккаунты.

Игровое ядро принадлежит серверу. Адаптеры преобразуют вход в команды и отображают
доступные пользователю проекции. Режимы могут иметь разные правила и модели;
общее ядро отвечает за участников, команды, события, дедлайны и доставку.

Дедлайны, восстановление и фоновые задачи исполняются независимо от транспорта.
Остановка бота должна быть проверяемым штатным сценарием. Доставка уведомления
может повторяться, но игровые последствия и награды применяются однократно.

Конкурентность проверяй на реальных сценариях: два игрока действуют одновременно,
один пользователь повторяет команду с другого клиента, worker закрывает фазу
в момент ответа. Проверяй фазу и допустимость действия, не создавай лишних
конфликтов общей revision между независимыми ходами.

## Переход со старой архитектуры

Оставшийся bridge — долг с конечным условием удаления. Не расширяй его.
Для каждого вызова: найди пользовательский сценарий, реализуй прямую команду,
проверь оба интерфейса, затем удали старый путь. Не сохраняй два независимых
источника очков или состояния. `Update.de_json` и `process_update` не являются
внутренним API приложения.

Для квиза ответ через приложение записывается общей командой. Если Telegram poll
не поддерживает нужное отображение внешнего голоса, выбери честное представление
через кнопки/карточку и опиши поведение; не имитируй голос пользователя.

Существующая `AlchemyService` в `storage/alchemy.py` и синхронизация отдельной
HTML-страницы не повод переписывать игру целиком. Переноси ответственность по
сценариям: общий вход, загрузка/слияние прогресса, проверка открытий и наград,
общая навигация. Для offline-игры сервер отличает локальные достижения от
проверенных рейтинговых результатов. Клиентская сводка не является доказательством
права на награду.

## Проверки по изменению

| Изменение | Достаточная проверка до интеграции |
| --- | --- |
| Документы / skill | ссылки, команды, skill validator, отсутствие ложных статусов |
| Правила игры | связанные unit-тесты, границы фаз, победа, запрещённые действия |
| Хранение / команды | реальные PG-тесты, повторы, гонки, откат транзакции |
| UI / синхронизация | JS-тесты и пользовательский сценарий в браузере |
| Telegram adapter | тот же сценарий и состояние через тестовый бот; секретные проекции |
| Миграция | отдельная тестовая БД, сверка данных, restore, совместимость версии |
| Релиз | полная матрица [RELEASE_CRITERIA](RELEASE_CRITERIA.md) |

Быстрые проверки инфраструктуры правил (без БД и токенов):

```powershell
python scripts/project_checks.py --worktree
python -m unittest discover -s tests -p test_project_checks.py
python -m unittest discover -s tests -p test_codex_hooks.py
```

JS-тесты текущего клиента:

```powershell
node --test tests/js/mini_navigation.test.cjs tests/js/alchemy_sync.test.cjs
```

Полный Python/PG gate выполняется в воспроизводимом dev-контуре:

```powershell
pwsh -File scripts/Test-LocalMilestone.ps1
```

Он собирает образ, пересоздаёт только `morning_quiz_test`, применяет миграции,
выполняет Alembic check, pytest и проверки backup/restore согласно конфигурации.
Не направляй этот скрипт на dev/production БД. Проверяй итоговые skipped и причины.
Для PR и push в `main` та же обязательная последовательность задана workflow
[`CI`](../../.github/workflows/ci.yml), использующим отдельную disposable PostgreSQL 17.
Dev-контейнер и CI ставят Python-набор из `requirements-local-lock.txt` с проверкой
хешей; отдельный тест не даст lock-файлу разойтись с прямыми зависимостями. Workflow
аудирует и dev/test lock, и разрешённый runtime `requirements.txt`, сохраняет их
CycloneDX SBOM вместе с JUnit-отчётом тестов на 14 дней. Обновляй lock через
`uv pip compile --generate-hashes --python-version 3.13 -o requirements-local-lock.txt
requirements-local-test.txt`.
Исторические `tests/run_all_tests.py` и `*_test.py` работают с прежним JSON-контуром
и не заменяют этот gate. Инструкции запуска: [LOCAL_DEVELOPMENT](../LOCAL_DEVELOPMENT.md).

Для Alchemy меняй исходники `minigames/alchemia-1.0/`, затем воспроизводимо собирай
`web/mini_client/alchemy.html`. Сборка обновляет `art.svg` и `CONTENT_REPORT.json`:
сверь весь полученный diff; не правь только генерируемый HTML. Проверяй хеш текущей
сборки, а не историческое число из старого отчёта.

## Автоматические хуки

Git hooks устанавливаются только в текущую копию:

```powershell
python scripts/install_project_hooks.py
```

Installer проверяет существующие настройки и не заменяет чужие hooks.
`pre-commit` проверяет индекс, `pre-push` — отправляемые ревизии. Проверки не
зависят от unstaged исправления поверх плохого staged-файла. Они обнаруживают
синтаксические ошибки Python, нарушение проверяемых границ слоёв, новые вызовы
legacy bridge и добавление известных путей секретов/операционных данных.

Это ограниченные статические gates: они не доказывают отсутствие всех костылей,
секретов в произвольном файле или ошибок продукта и не заменяют ревью и приёмку.
Существующий долг не становится разрешением добавлять новые обходные пути.
Локальные hooks можно отключить средствами Git; серверное обязательное требование
проверок на GitHub нужно настраивать отдельно при работе с правилами репозитория.

Codex hooks описаны в `.codex/hooks.json`:

- `SessionStart` напоминает корень, правила и границы готовности.
- `Stop` выполняет read-only быструю проверку и сообщает ошибки. Он не заставляет
  агента бесконечно продолжать чат и не требует исправлять чужой исходный diff.

Codex требует доверия к точному определению hooks. Открой `/hooks` в CLI проекта,
проверь команды и подтверди доверие. До этого lifecycle hooks могут быть пропущены;
Git hooks работают независимо. Не обходи trust программной записью или флагом bypass.
Если Codex открыт в production-копии на `Z:`, skills из dev-копии автоматически
не относятся к этому корню; для разработки открой dev-проект.

Форматы сверены 2026-10-07: [Codex hooks](https://learn.chatgpt.com/docs/hooks),
[project skills](https://learn.chatgpt.com/docs/build-skills).

## Отчёт и передача работы

Укажи изменённое поведение, актуальную ревизию/незакоммиченный diff, реально
выполненные проверки и оставшиеся ограничения. Для существенного изменения
нужна независимая проверка подходящей моделью. Не ставь `ready`, если обязательный
сценарий не выполнен; используй «реализовано, приёмка не пройдена».

При паузе оставь короткую запись в задаче: готовый срез, известная проблема,
следующий шаг и свидетельства проверки. Не заводи отдельные журналы для каждой
мелкой правки и не смешивай состояние dev с production.
