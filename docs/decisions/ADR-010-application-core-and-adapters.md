# ADR-010: Morning Quiz — приложение с внешними адаптерами

Статус: `accepted` для dev. Дата: 2026-09-01. Задача: MQB-005.
Заменяет ADR-009 в части, где PTB application и Telegram handlers считались
центром игровой логики.

## Контекст

Проект вырос из Telegram-бота, поэтому создание вопросов, переходы игры,
настройки и доставка часто соединены внутри обработчиков Telegram. После появления
Mini App это приводит либо к повторной реализации функций, либо к имитации
Telegram-сообщений для работы приложения. Мафия сразу показала ту же проблему:
экран Mini App появился раньше равноправного чатового интерфейса.

Продуктом является Morning Quiz: игры, профиль, прогресс, настройки, расписания и
администрирование. Telegram — одна из сред доступа к продукту, а не источник его
состояния и правил.

## Решение

Разделить систему на четыре уровня:

1. **Домен и прикладные сценарии** формируют вопросы, фазы, результаты, очки,
   настройки и разрешённые действия. Они не импортируют Telegram, FastAPI или DOM.
2. **PostgreSQL и repositories** хранят единое состояние, идемпотентность и
   историю переходов.
3. **Адаптеры** переводят входы и выходы: Telegram Bot API, Mini App API,
   локальная админка и offline/dev transport.
4. **Представления** решают, как показать уже сформированное состояние: сообщение,
   poll, карточка Mini App или экран панели.

Одна команда пользователя должна превращаться в один application command с
идемпотентным ID. Ядро возвращает новое состояние и набор событий. Telegram-адаптер
может отправить poll/сообщение, Mini App — JSON-проекцию; ни один транспорт не
пересчитывает результат самостоятельно.

Telegram-бот сохраняется как полноценный пользовательский интерфейс: команды,
inline-кнопки, уведомления, групповые права и запуск Mini App. Слово «бот» далее
обозначает только Telegram-адаптер, а не всю программу.

## Переходный период

Переписывание одним релизом отклонено как слишком рискованное. Функции переносятся
вертикальными сценариями:

1. общий game/application service;
2. PostgreSQL state и тесты без транспорта;
3. Mini App adapter;
4. Telegram adapter;
5. удаление старого формирования состояния из handlers после проверки паритета.

По состоянию на 2026-10-09 прямые маршруты Mini App для Classic и Photo используют
общие application services (`application/classic.py`, `application/photo.py`),
состояние живёт в PostgreSQL, а события доставки проходят транзакционный outbox
(`NotificationQueue` → `handlers/mafia_handlers.py`). Legacy MiniBridge, его
PTB-worker, очередь действий, runtime/media API и клиентский fallback удалены из
dev-контуров. Mini App не создаёт synthetic `telegram.Update` и не отправляет
действия через `Application.process_update`.

Ответ из Mini App является игровым действием, но не поддельным голосом в
нативном Telegram poll: запись общего результата/ledger выполняет application
service. Повтор команды с тем же `command_id` возвращает сохранённую квитанцию.
Тестовый Telegram transport остаётся отдельным egress allowlist для реального
приватного test-bot и не участвует в игровых командах Mini App. Проверка полного
Bot↔Mini App цикла на одной PostgreSQL-партии остаётся отдельным acceptance gate.

## Последствия

Dev-срез 2026-10-09: `RoomPhotoApplicationService` использует общий Photo domain,
каталог и scoring с явными `room_id`/`creator_account_id`, без fake Telegram IDs.
Owner комнаты управляет своей личной creator-only серией; другие участники видят
только занятость. Room deadlines исполняются worker по `game_id`, Telegram paths
отфильтровывают `chat_id IS NULL`. Очки серии сохраняются в game state и не сливаются
с историческими Telegram-баллами. Это не решение групповой Photo-политики AUD-019
и не свидетельство браузерной/WebView приёмки.

- Mini App и Telegram обязаны иметь матрицу функционального паритета.
- Исправление правила игры делается один раз в ядре.
- Telegram API можно обновлять независимо от правил игры.
- Появляется дополнительный слой application services и события доставки.
- На время миграции будут сосуществовать legacy handlers и новые use cases;
  граница каждого перенесённого сценария фиксируется тестами и документацией.

## Проверка

- Доменный тест проходит без Telegram token, HTTP и браузера.
- Один и тот же сценарий запускается через Telegram- и Mini App-adapter и даёт
  одинаковое состояние/очки.
- Вызов одного request ID через разные интерфейсы не удваивает действие.
- Ни один публичный projection не раскрывает будущие ответы, чужие данные или
  скрытые роли.
