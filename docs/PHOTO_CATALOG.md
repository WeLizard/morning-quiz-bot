# Фото-каталог: загрузка и подготовка новых вопросов

Локальная часть MQB-001, проверена 2026-08-30. Production не читался и не менялся.

## Работа в панели

В разделе «Фото-квиз» доступны добавление изображения с ответом, просмотр,
поиск по ответу/имени, фильтры включённых/отключённых/отсутствующих изображений
и страницы по 24 записи. Редактор сохраняет ответ, hints и enabled с проверкой
версии. Отключение сохраняет файл и историю; физического удаления и замены
изображения в этом этапе нет. Изменения действуют на подготовку новых серий.
Маски подсказок в игре по-прежнему вычисляются из ответа; JSON hints не является
новым конструктором правил подсказок.

Загрузка принимает JPEG, PNG, WebP, не анимацию: максимум 10 МиБ, 20 млн
пикселей, соотношение сторон не более 20:1. Сервер декодирует содержимое, а не
доверяет расширению/MIME, учитывает EXIF orientation, уменьшает длинную сторону
до 2048 px и сохраняет новый WebP без EXIF/GPS/ICC. Исходник на компьютере
пользователя не изменяется, на сервере хранится подготовленная копия.
Декодирование/размеры и поворот основаны на API
[Pillow Image](https://pillow.readthedocs.io/en/stable/reference/Image.html) и
[ImageOps.exif_transpose](https://pillow.readthedocs.io/en/stable/reference/ImageOps.html#PIL.ImageOps.exif_transpose).
Это ограничения приложения, а не заявление о поддержке всех клиентов Telegram.

## API и повтор запроса

`POST /api/photo-quiz/uploads/{upload_id}?correct_answer=...&enabled=true`
принимает сырые байты изображения, `Content-Type: application/octet-stream`.
`upload_id` — 32 строчные hex-цифры UUID; в UI он создаётся один раз на форму.
Нужны сессия администратора и CSRF, как для остальных административных API.
Объём контролируется при чтении stream, без multipart-спулинга. Одновременно
допускаются две загрузки на процесс, ожидание/чтение/обработка ограничены 60 с.

Результат: 201 при создании, 200 при повторе. Повтор с тем же ID, исходными
байтами, ответом и enabled не создаёт второй вопрос и не отменяет последующую
правку его метаданных. Другие данные с тем же ID дают 409. После обрыва связи
повторять запрос **в той же форме**; новая форма создаёт новый ID. Повтор после
перезагрузки страницы не дедуплицируется автоматически по содержимому файла.
422 означает некорректный файл/параметры, 413 — размер, 408 — таймаут,
503 — ошибка файлового ввода/вывода. Неперенесённые старые write API закрыты.

## Согласованность файлов и БД

Имя файла генерируется сервером: `mqb-upload-<uuid>-photo.webp`; исходное имя
не используется как путь или ответ. Окончание не числовое, чтобы существующая
группировка фото-вариантов не обрезала часть идентификатора.

Запрос берёт PostgreSQL advisory lock для ID загрузки и row lock для существующей
записи. Полностью записанный временный файл публикуется через атомарный hard link
без перезаписи занятого имени; затем фиксируется запись каталога. Нужна файловая
система с поддержкой hard links (проверено на локальном NTFS). Не считать это
распределённой транзакцией между диском и PostgreSQL.

При сбое до commit может остаться файл без записи БД. Бот **не подбирает** такие
managed-файлы и не создаёт ответ из их имени. Повтор того же запроса использует
совпадающий файл и завершает запись. Старые legacy-файлы без записи каталога
сохраняют прежнюю автоподготовку метаданных. Незавершённые `.part` после аварийного
завершения процесса и бесхозные managed-файлы не удаляются автоматически.
Их уборка требует отдельной сверки с БД; не удалять каталог целиком.

Существующий файл никогда не заменяется другой картинкой. Неизвестный исход
commit не приводит к удалению файла: запись в БД могла уже сохраниться.
Для повторной подготовки после смены кодека/версии Pillow нужна отдельная
политика миграции медиа; текущий алгоритм не перезаписывает прежние байты.

## Каталоги и резервирование

`PHOTO_IMAGES_DIR` задаёт общий каталог для бота и PG-админки. По умолчанию это
абсолютный `data/images` текущего проекта. Preview принудительно использует
`.local/preview/images`; основной каталог не копируется и не изменяется.
Тестовый вопрос в preview отключён и не является игровым контентом production.

Резервная копия должна включать **дамп PostgreSQL и каталог изображений**.
Один `pg_dump` не сохраняет бинарные картинки. Перед согласованной резервной
копией остановить writers, скопировать оба компонента, проверить ссылки и
контрольные суммы (`image_sha256` у новых загрузок). Не удалять файлы по признаку
enabled=false: на них могут ссылаться сохранённые серии.
Реальный backup/cutover production в этом этапе не выполнялся.

- Полная совокупность тестов: **171 passed, 0 failed, 0 skipped**, 21 прежнее
  предупреждение. 163 теста — в отдельной временной БД; 8 сквозных — в собственных
  изолированных схемах локальной test DB, включая `pg_dump/restore`.
- Отчёты: `.local/acceptance/photo-regression.xml`, `photo-acceptance.xml`.
- Новые проверки: `tests/test_photo_upload.py` — форматы, повреждения, анимация,
  EXIF, размеры, неизменяемая публикация, авторизация/CSRF, повторные и параллельные
  запросы, откат, игнорирование бесхозного файла, выбор/отключение фото ботом.
- `alembic check`: новая миграция не требуется. JS проходит `node --check`.
- В браузере: форма 320/390 px, показ загруженного через HTTP API изображения,
  изменение ответа, фильтры и пустая выдача. Автоматическая передача файла через
  системный диалог браузера не проверялась; бинарная загрузка проверена API.
- Живых отправок Telegram не было; транспорт игровых тестов — mock.
