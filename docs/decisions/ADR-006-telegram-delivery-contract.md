# ADR-006: Отправка Telegram без слепых повторов

Статус: `accepted`. Дата: 2026-08-30. Область: локальный этап MQB-001.

## Контекст

Telegram sendPoll/sendMessage не принимают idempotency key. Потерянный HTTP-ответ
не доказывает, что сообщение не создано. Общий retry мог повторить опрос или
весь длинный текст после ошибки его последней части. BadRequest наследуется
от NetworkError и ошибочно попадал в сетевой retry.

## Решение

- PTB 22.8 закреплён в отдельной `.venv-local`, глобальная среда не обновляется.
- Общий транспорт различает явный 429, ошибку запроса и неизвестный исход.
  429 допускает до двух повторов с суммарным ожиданием до 30 секунд;
  RetryAfter принимается числом или timedelta. Чужие чаты не блокируются.
- Неидемпотентная отправка после timeout/NetworkError не повторяется. Редактирование
  и удаление известных сообщений допускают ограниченные повторы.
- После ожидания опрос и пояснение повторно проверяют текущую сессию/доступ.
- Классика сохраняет ровно один верный вариант; обычный текст не экранируется
  Markdown. Стабильные ID вариантов сохраняются в существующем PG checkpoint.
- Пояснение публикуется после дедлайна. Перед отправкой сохраняется intent,
  после подтверждения — ID для очистки. Неизвестный результат не воспроизводится
  при рестарте. Старые snapshots без новых полей остаются читаемыми.
- Части длинного текста имеют отдельные повторы. Ошибка после подтверждённых
  частей не запускает заново весь текст. Форматированный длинный текст требует
  предварительной подготовки страниц; автоматически разрывать entities нельзя.

## Последствия и альтернативы

Выбрана защита от автоматических дублей, **не exactly-once доставка**. При
таймауте возможно пропущенное сообщение либо уже созданное, чей ID неизвестен
для последующего удаления. Необратимо доказать отсутствие сообщения через API
бот не может. Повторять всё «на всякий случай» отвергнуто.

Для серверных переходов Mafia позднее добавлен PostgreSQL outbox (ADR-011):
явный 429 теперь допускает отложенное возобновление после рестарта, а неизвестный
результат остаётся `uncertain` без автоматической повторной отправки. Legacy
отправка квиза пока использует описанный выше локальный контракт. У её caller'ов
успешный длинный send по-прежнему возвращает только первый ID; учёт всех частей —
отдельная работа. Изменение накопленных очков не требуется.
