# ADR-001 — PostgreSQL как основное хранилище

- **Статус:** `accepted`
- **Дата:** 2026-08-30
- **Связанные задачи:** [MQB-001](../tasks/MQB-001-postgresql-and-mini-app-foundation.md)
- **Заменяет:** нет

## Контекст

Morning Quiz Bot хранит изменяемые данные в JSON-файлах и частично в PTB
`PicklePersistence`. Бот обрабатывает updates конкурентно, а FastAPI-админка
может работать отдельным процессом и напрямую изменять те же данные.

Планируется Telegram Mini App и возможный отдельный игровой домен «Ночной
город». Это добавит авторизованный HTTP API, фоновые переходы состояния и больше
конкурентных операций. Новое хранилище должно обеспечивать транзакции,
ограничения целостности, безопасные миграции и дальнейший рост без повторной
смены технологии.

## Рассмотренные варианты

### Сохранить JSON/Pickle

Минимум новых зависимостей, но отсутствуют надёжные транзакции между
сущностями, ограничения целостности и безопасная конкурентная запись из бота и
веб-приложения. Вариант не решает исходную проблему.

### SQLite

Простой запуск и единый файл резервной копии. Подходит для одного процесса и
умеренной нагрузки, но все записи сериализуются одним writer. При одновременной
работе бота, Mini App, админки и фоновых задач потребуются дополнительные
ограничения и останется вероятность будущего переезда на серверную СУБД.

### PostgreSQL

Требует отдельного сервиса, управления соединениями и полноценных процедур
backup/restore. Взамен предоставляет конкурентные транзакции, строгие
ограничения, зрелые инструменты миграции и подходящую основу для Telegram Mini
App и игрового backend.

## Решение

Использовать PostgreSQL как единственный источник истины для изменяемых
операционных данных.

Доступ реализовать через SQLAlchemy 2 async с драйвером `asyncpg`, а изменения
схемы — через Alembic. Бот, FastAPI и будущие игровые модули работают через
общие repository/service interfaces и не выполняют SQL из Telegram handlers или
frontend-кода.

Статический банк вопросов, тексты и конфигурация могут оставаться в JSON, пока
их перенос не даст отдельной практической пользы. Redis не вводится этим
решением и может быть добавлен позже только как coordination/cache layer, но не
как источник истины.

## Последствия

- В Docker Compose появляется PostgreSQL service, healthcheck и постоянный
  volume.
- Для локальной разработки требуется доступная PostgreSQL database.
- Строка подключения и credentials передаются через environment/secrets и не
  попадают в репозиторий.
- Нужны ограниченный connection pool, startup retry и короткие transaction
  boundaries.
- Перед запуском новой версии применяются Alembic migrations.
- Резервное копирование меняется с копирования JSON на проверяемый PostgreSQL
  dump/restore; исходные JSON сохраняются как migration snapshot на переходный
  период.
- PostgreSQL становится общей инфраструктурой для викторины, Mini App и
  «Ночного города», при этом доменные таблицы и сервисы остаются разделёнными.

## Проверка решения

- Интеграционные тесты выполняются на PostgreSQL с актуальными Alembic
  migrations, а не на подменной SQLite database.
- Проверяются конкурентные ответы, повторная обработка события и рестарт во
  время активной викторины.
- Наблюдаются использование пула, время транзакций, ошибки соединения и размер
  БД.
- Процедура backup/restore проверяется до удаления переходных JSON snapshots.

Решение пересматривается только при появлении подтверждённых эксплуатационных
ограничений PostgreSQL или изменении модели развёртывания проекта.
