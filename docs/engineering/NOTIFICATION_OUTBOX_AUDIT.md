# Безопасная проверка notification outbox

Скрипт `scripts/audit_notification_outbox.py` строит диагностический отчёт о
`pending`, `sending`, `uncertain`, `resolved` и `delivered` уведомлениях. Он не отправляет,
не повторяет и не разрешает уведомления. Неизвестный результат Telegram нельзя
переотправлять вслепую: сначала нужно сверить конкретное действие и затем принять
отдельное операторское решение.

Команда требует явно заданный `TEST_DATABASE_URL` и принимает только локальную
одноразовую БД `morning_quiz_test` (на хосте `127.0.0.1:55433`, в dev-контейнере
`postgres:5432`; пользователь `mqb_dev`). `DATABASE_URL` не используется.

```powershell
$env:TEST_DATABASE_URL = 'postgresql+asyncpg://mqb_dev:...@127.0.0.1:55433/morning_quiz_test'
.venv-local\Scripts\python.exe scripts\audit_notification_outbox.py
```

Отчёты сохраняются в `.local/acceptance/notification-outbox-audit.{json,md}`.
Отдельно показываются зависшие `sending` старше пяти минут и ограниченный список
`uncertain` с типом последней ошибки. Тела уведомлений и секреты в отчёт не входят.
Ненулевой код завершения означает, что найдены зависшие или неопределённые записи,
а не то, что скрипт исправил их.

Это проверка тестовой БД, а не production-операторская панель или процедура
согласования. Не используй для боевой базы и не считай отчёт доказательством
успешной доставки.

## Сверка в локальной dev-админке

На экране «Управление и обслуживание» есть блок «Уведомления · проверка доставки».
Он требует обычного входа в локальную админку; изменение защищено CSRF. Список
показывает безопасные метаданные, но не тело сообщения, сырой текст ошибки или
сохранённые доказательства. `sending` доступен только для чтения: даже если запись
старая, это не доказывает, что отправитель остановился или Telegram отказал.

Для `uncertain` открой карточку, проверь конкретное сообщение вне панели и явно
выбери одно из двух решений:

- «Подтвердить доставку» — только если найдено именно это сообщение; запиши chat ID,
  message ID, способ проверки и причину.
- «Закрыть без повторной отправки» — если результат нельзя достоверно сопоставить
  или уведомление уже неактуально; запиши способ проверки и причину. Это **не**
  утверждение, что сообщение не было доставлено.

Оба решения переводят запись в `resolved` с квитанцией; ни одно не отправляет
Telegram-сообщение повторно и не меняет игру, баллы или привязку Classic poll.
Если Classic-опрос действительно появился, одного message ID недостаточно для
восстановления приёма ответов: для этого отдельно нужны poll ID и проверенная
связь вариантов. При конфликте версии обнови карточку и сверяй заново. После
ошибки сети повторяй действие в той же открытой форме: она сохраняет тот же
`action_id` и тело запроса. После нового входа форма не восстанавливается;
проверь список `resolved`/`uncertain` перед новой попыткой.

Админка использует один общий ключ и пишет в квитанцию роль `local-admin`.
Это не персональный аудит людей, знающих ключ. Реальные Telegram-клиенты,
production-процедура пока не принята. Offline-карантин `sending` описан ниже;
его реализация не является свидетельством остановки реальных отправителей.

## Версия попытки отправки

Каждый `claim` сохраняет новую версию записи. Завершение, явный отложенный повтор
после 429 и отметка неизвестного результата принимают только версию именно этой
попытки. Поздний callback старого процесса с тем же worker ID больше не может
изменить новую попытку. Это защита записи PostgreSQL, а не остановка внешнего
HTTP-запроса: осиротевшее `sending` по-прежнему нельзя автоматически возвращать
в `pending` или закрывать в онлайн-панели. Для его карантина сначала нужно
подтвердить остановку всех отправителей; для dev реализована отдельная offline-команда.

## Offline-карантин осиротевшего sending (только dev)

`scripts/quarantine_notification_outbox.py` адресно переводит одну запись
`sending → uncertain`, увеличивает версию и сохраняет отдельную
`notification_quarantine_receipts` квитанцию. Миграция `20261009_0023` добавляет
только эту таблицу, существующие записи не меняет. Это не terminal resolution:
затем оператор отдельно сверяет доставку и при необходимости использует обычное
решение для `uncertain`. Карантин не повторяет отправку, не подтверждает доставку,
не меняет игру, баллы, Classic poll binding или количество попыток.

Перед запуском нового storage-кода нужна схема `0023`: проверка общего action UUID
использует новую таблицу также в terminal resolve. Не перезапускай новый admin
код на схеме `0022`; в текущем срезе persistent dev не мигрировалась.

До команды оператор независимо проверяет полный список отправителей во всех
deployments: Telegram profile Compose, отдельные runner/process/service и другие
машины, которые имеют тот же доступ к outbox/боту. Все отправители должны быть
остановлены, внешние HTTP-операции завершены, автоматический restart отключён на
время действия. Проверка только локального контейнера, возраст lease, версия БД
или attestation строка не доказывают остановку всех отправителей. Если это нельзя
подтвердить, карантин не применяют. CLI не проверяет процессы автоматически.

Сохрани без секретов JSON-свидетельство вне Git, например
`.local/acceptance/quarantine-evidence.json`, с непустыми строками
`verification_method` (кто, когда и как независимо проверил остановку/отсутствие
in-flight HTTP) и `sender_inventory` (полный список проверенных отправителей и их
состояние). Не записывай токен или тело уведомления. Отдельным чтением получи
точные `id`, `version`, `claimed_by`, `claimed_at`; null указывается буквально
`null`. Нет массовой операции или выбора по возрасту.

URL берётся только из явно названной переменной процесса; `.env`, дефолтный
`DATABASE_URL` и production-конфигурация не читаются. Guard разрешает пользователя
`mqb_dev`, БД `morning_quiz_dev`/`morning_quiz_test`, endpoint
`127.0.0.1:55433` либо `postgres:5432` внутри dev-контейнера. Query-параметры URL
запрещены. Передавай имя переменной, а не пароль в аргументах/истории команд.

```powershell
.venv-local\Scripts\python.exe scripts\quarantine_notification_outbox.py `
  --database-url-env MQB_QUARANTINE_DATABASE_URL `
  --item-id '<observed-id>' --expected-version 1 `
  --expected-claimed-by '<observed-worker>' `
  --expected-claimed-at '<observed-ISO-timestamp-with-timezone>' `
  --action-id '<fresh-UUID>' --operator-id '<operator>' `
  --reason '<reason>' --evidence-file '.local/acceptance/quarantine-evidence.json' `
  --senders-stopped-attestation ALL_TELEGRAM_SENDERS_INDEPENDENTLY_CONFIRMED_STOPPED
```

Без `--apply` выполняются те же проверки под блокировкой строки и откат всей
транзакции; квитанция в БД не сохраняется. После ручной проверки добавь `--apply`
к тому же запросу. Apply снова сверяет статус, версию, отправителя и timestamp.
При конфликте перечитай запись и повторно проверь ситуацию. После неоднозначного
сетевого результата повторяй строго тот же action UUID и тело запроса: сохранённая
квитанция возвращается без новой записи/перехода, даже после последующего terminal
resolution. Изменённый запрос с тем же UUID отклоняется. UUID нельзя использовать
одновременно для карантина и terminal resolution. Квитанция переживает удаление
игры/outbox; автоматический downgrade с удалением аудита запрещён.

Attestation и свидетельство фиксируют утверждение оператора; CLI не представляет
их как автоматическую проверку. Вывод содержит только безопасную квитанцию,
не URL/пароль, payload или evidence. Успешный dry-run не является разрешением
на применение к persistent dev или production. Реальная остановка и карантин
рабочих записей в текущем срезе не выполнялись; production не поддерживается.
