# Farm 0.2.0 в QuizzyWizzy

Farm — уже реализованный игровой режим в `qw_farm/`, а не отдельный бот или
локальная SQLite-игра. Текущая dev-интеграция и незакрытые приёмочные ворота:
[MQB-007](tasks/MQB-007-farm-020-integration.md).

## Контракт платформы

- Хранение: единственная PostgreSQL платформы. `farm_states` содержит
  версионированное игровое состояние, `farm_receipts` — идемпотентные результаты,
  `farm_ledger` — экономический журнал. Таблицы добавляет `qw_farm_010`;
  `qw_farm/demo.py` и SQLite-профили не используются host-адаптером.
- Аккаунт: существующий `Account` гостя или Telegram-пользователя. Cookie
  проверяет host, затем Farm-команда работает в той же транзакции. При двух
  действующих cookie клиент обязан указать `identity=guest|telegram`.
  Приглашение — публичный указатель на ферму, не credential и не способ
  восстановить чужой аккаунт.
- Блокировка/maintenance: сначала общий platform fence, затем host-сессия и
  Account, затем отсортированные Farm advisory locks. На Account используется
  `NO KEY UPDATE`, совместимый с FK-проверкой `KEY SHARE` при встречных визитах.
- Игра: сервер проверяет действия, квоты, дедлайны, ресурсы и соседские права;
  клиент отправляет команды с `command_id` и повторяет тот же ID при неясном
  ответе. Монеты Farm не конвертируются в баллы квиза.
- UI: `/app/farm`, ассеты `/app/farm/assets/`, API `/api/farm/v1/...`.
  Главная QuizzyWizzy показывает режим только при `QW_FARM_ENABLED=1`.
  Telegram `startapp=farm_<UUID>` и обычная веб-ссылка передают подсказку о
  приглашении через вход; проверка личности остаётся за host-сессией.
  При наличии `MINI_APP_BOT_USERNAME` приглашение открывает зарегистрированный
  Direct Mini App: `https://t.me/<bot>/play?startapp=farm_<UUID>`.
  `MINI_APP_SHORT_NAME` задаёт short name (по умолчанию `play`, как в BotFather).
  Telegram, системная отправка и копирование используют эту ссылку; почта
  предпочитает HTTPS web URL. Без имени бота сохраняется самостоятельная web-ссылка.

## Локальная эксплуатация

В `compose.dev.yml` Farm смонтирована read-only во все Python-сервисы, но флаг
включён только у `mini-app`. Production-конфигурацию не менять. До миграции
заполненной базы нужен проверенный backup. Для dev уже сохранён архив, путь и
хэш приведены в MQB-007. Не откатывать миграцию с игровыми данными; для
временного выключения режима убрать флаг у Mini App и пересоздать только его.

Проверки: `python -m pytest -q` в закреплённом dev-образе, `node --test
tests/js/farm_sharing.test.cjs`, `node --test tests/js/mini_navigation.test.cjs`,
отдельные PostgreSQL `test_farm_platform.py` и `test_farm_migration.py` на
`morning_quiz_test`. Нативный браузер и Telegram WebView — отдельные проверки;
DOM+HTTP harness из пакета не заменяет их.

## Общие HTTP-квоты (выключены по умолчанию)

Контролируемый dev-срез `QW_FARM_SHARED_RATE_ENABLED=1` заменяет локальный
IP-счётчик Farm и дублирующий host-счётчик для `/api/farm/v1/` общей квотой
PostgreSQL. Origin, CSRF, Sec-Fetch-Site, адрес сервиса и host-аутентификация
остаются обязательными. Статическая страница и другие API используют прежнюю
защиту host. Флаг не добавлен в Compose и не включён в постоянном dev-контуре.

Перед включением нужна additive-миграция `qw_farm_011` и отдельный случайный
`QW_FARM_RATE_SECRET` не короче 32 байт, одинаковый у всех workers. Токен бота
переиспользовать нельзя. Потеря/смена секрета сбрасывает доступ к прежним
бакетам; при ротации переключай workers согласованно. Отсутствие/короткий
секрет останавливает сборку приложения, отсутствие таблицы останавливает
startup. Ошибка/таймаут БД при квоте даёт `503 rate_unavailable`; обхода через
локальный счётчик нет. Откат режима — выключить только новый флаг; таблица
и игровые данные сохраняются, downgrade этой миграции запрещён.

Каждая квота — скользящие 60 секунд по времени PostgreSQL после блокировки
строки. Read означает GET/HEAD, остальные методы относятся к write.

| Переменная | По умолчанию | Ключ |
| --- | --- | --- |
| `QW_FARM_RATE_IP_READ` | 600 | IP + read |
| `QW_FARM_RATE_IP_WRITE` | 120 | IP + write |
| `QW_FARM_RATE_ACCOUNT_READ` | 240 | проверенный Account UUID + read |
| `QW_FARM_RATE_ACCOUNT_WRITE` | 60 | проверенный Account UUID + write |

Значения — целые от 1 до 10000; конфигурация всех workers должна совпадать.
IP берётся только из нормализованного `request.client.host` (IPv4-mapped IPv6
приводится к IPv4); сырой X-Forwarded-For не используется. Если proxy передаёт
peer, доверие к нему задаётся настройкой сервера вне Farm; Compose уже запускает
Uvicorn с `--no-proxy-headers`. IP и UUID в таблице заменены HMAC-SHA256,
секрет и cookies в неё не записываются. Разные аккаунты за NAT разделяют
IP-квоту, но имеют отдельные account-квоты; смена IP/worker не сбрасывает
account-квоту. Эти значения — стартовые настройки, не результат нагрузочного
исследования и не замена внешней защиты от распределённого потока.

Сначала проверяются HTTP-границы, затем отдельная IP-транзакция. Для игровых
endpoint следующая короткая транзакция выполняет fence → host auth/locks →
account quota и commit. Игровая транзакция заново проверяет auth/moderation
и использует прежний порядок Farm locks; вложенного checkout соединения нет.
Ошибки игровых правил, откаты, lost-response retries и идемпотентные replay
сохраняют списание квоты. Анонимный запрос расходует только ingress, ошибки
origin/CSRF/Sec-Fetch-Site не расходуют квоту; неверная структура команды
отклоняется до account preflight. `/config` публичен и расходует только IP.

`429 rate_limit` возвращает целый `Retry-After` от 1 до 60 секунд до выхода
старейшего принятого запроса из окна и `Cache-Control: no-store`. Для read
и write окна независимы. Preflight ограничен 3 секундами, включая ожидание
соединения/блокировок. Таблица хранит максимум текущего лимита timestamps
на бакет; после снижения лимита старые timestamps естественно истекают.
TTL бакета — 60 секунд после последнего принятого запроса. Очистка не имеет
нового scheduler: ingress opportunistically удаляет максимум 100 истёкших
строк не чаще раза в минуту на процесс, с индексом expiry и SKIP LOCKED.
В отсутствие запросов строки сохраняются; при большом потоке новых subjects
физическая очистка может отставать, хотя просроченные timestamps уже не влияют
на квоту. Строгой границы общего числа бакетов эта защита не обещает.

Farm UI учитывает `429` до разбора JSON и показывает секундный отсчёт в
статусе соединения. Целый `Retry-After` ограничен 1–60 с; отсутствующий,
повреждённый или HTTP-date заголовок использует fallback 5 с согласно
секундному контракту Farm. Read/write ожидания раздельные: read-отказ
сдерживает poll/focus/ручное обновление, write-отказ — новые команды и повтор.
Кнопка «Повторить» отключена на время соответствующего ожидания; после его
окончания требуется нажатие, автоматической записи нет. При `429` pending
команда и её `command_id` сохраняются, включая повтор после потерянного ответа.
Успешная запись не становится pending из-за `429` следующего чтения. После
отказа начальной загрузки retry снова загружает config/start. При скрытой
игровой области отсчёт показан на экране входа; его кнопка повторения
остаётся доступной после окончания ожидания. Отсчёт использует
существующий секундный UI timer, не создавая новый timer на каждый отказ.
Это подсказка и защита от лишних запросов в текущей вкладке; сервер остаётся
источником квот, перезагрузка вкладки не отменяет серверное ограничение.
Focused regression: `node --test tests/js/farm_rate_limits.test.cjs`.

Приёмка с disposable PostgreSQL: `tests/test_farm_rate_limits.py` проверяет
две ASGI-инстанции, общий Account при смене IP, NAT, отдельные read/write,
CSRF/XFF, expiry/Retry-After, bounded cleanup, rollback/replay, ошибки БД,
повторную аутентификацию и отсутствие вложенных транзакций. Проверки этой
задачи и открытые ворота записываются в MQB-007; публичный выпуск не включён.
