# Mini App: отдельный пользовательский API

Исходный read-only этап MQB-001 проверен 2026-08-30. На 2026-09-01 подключены
экраны, временный HTTPS, прямые игровые проекции/ответы классики и фото, нативные
личные настройки и DB-backed лобби/действия мафии. Полный асинхронный цикл Mafia
ещё не готов. Основной путь Classic/Photo использует прямые игровые API и отдельный
экран подготовки: настройки Classic читаются из общей проекции чата, параметры Photo
выдаёт backend. Для запуска этих режимов PTB-транскрипт не нужен; bridge остаётся
только для ещё не перенесённых legacy-сценариев.
[Игровые функции и оставшиеся сценарии](MINI_APP_GAMEPLAY.md).

## Граница сервисов

- `web.main` — прежняя локальная админка на 4184.
- `web.mini_app:create_app` — отдельное ASGI-приложение на 4185 в локальном тесте.
  Оно не импортирует админку, не монтирует её маршруты/статику и не читает `.env`.
- Общая PostgreSQL, отдельный `MINI_APP_DATABASE_URL`. В production нужны отдельные
  учётные данные БД и отдельный HTTPS origin. Этот перенос не выполнялся.
- По умолчанию фабрика read-only, кроме таблицы коротких сессий. Явный
  `runtime_enabled=True` добавляет ограниченную очередь действий общего runtime;
  только dev-фабрики включают её. Правка банка/системное администрирование не добавлены.

`GET /api/mini/config` отдаёт канонический каталог режимов `game_modes`:
стабильный `id`, название, состояние (`available`, `development` или
`coming_soon`), поддерживаемые интерфейсы и подтверждённые возможности. Главная
Mini App строит список режимов по этому manifest; `coming_soon` не имеет команды
запуска.

`GET /api/mini/photo/chats/{chat_id}/current` — read-only projection;
`POST .../sync` — авторизованное выполнение просроченных переходов и получение
обновлённой проекции. Чтение само по себе не меняет состояние игры.

### Игровые маршруты при runtime_enabled

- `GET /api/mini/runtime`: только собственные отображаемые сообщения, кнопки,
  варианты, таймер и результаты. Правильный ответ/пояснение скрыты до собственного
  записанного ответа. Никаких сырых checkpoints, чужих mailbox или путей файлов.
- `POST /api/mini/runtime/actions`: максимум 4 КБ JSON, idempotency `request_id`,
  тип command/callback/vote/text. Identity берётся из сессии cookie или legacy Bearer. Команды из
  белого списка; callback сверяется с текущей карточкой/revision, голос с дедлайном,
  фото-ответ с раундом. Очки/правильность не принимаются от клиента.
- `GET /api/mini/runtime/media/{message_id}`: авторизованное фото собственной
  карточки, только разрешённый локальный media root. Токен не передаётся в URL.

Worker в private dev runner пока выполняет классический и фото-квиз в той же PTB
Application, что и Telegram. Это переходный bridge, а не место для новой логики.
Счёт/достижения/параметры — существующие сервисы; данные `system_states`
нужны только для ограниченных очереди и представления. UI опрашивает API без
ручной верхней кнопки обновления. При неизвестном исходе повтор использует тот же
request ID; после падения running не исполняется автоматически ещё раз.
[Целевая архитектура приложения и адаптеров](decisions/ADR-010-application-core-and-adapters.md).

«Ночной город» bridge не использует: `MafiaApplicationService` выполняет команды,
дедлайны и безопасные проекции, а HTTP и Telegram только проверяют вход и
отображают результат. Тайные действия Telegram выполняются в личной карточке.

## Вход и сессия

Клиент отправляет `POST /api/mini/session`, JSON `{ "init_data": "..." }`, где
строка взята из `Telegram.WebApp.initData`. Отдельные `user_id`, `initDataUnsafe`,
cookie админки и query-параметр с токеном не принимаются.

Проверяется Telegram HMAC-SHA256: отсортированные декодированные поля, кроме
`hash`; если присутствует `signature`, она тоже входит в HMAC. Это не отдельный
алгоритм Ed25519 для третьих сторон. Время `auth_date` — не старше 5 минут,
допустимое опережение часов — 30 секунд. Нужна синхронизация серверных часов.
Дубликаты полей/JSON-ключей, повреждённое кодирование и неверный ID отклоняются.
Алгоритм сверён с [документацией Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

После проверки разрешён вход только существующему незаблокированному игроку.
Из входа не перезаписываются имя, профиль или очки. Ответ содержит время истечения;
секрет выдаётся только в cookie:

```json
{
  "expires_in": 900,
  "expires_at": "<UTC ISO-8601>"
}
```

Сервер ставит same-origin cookie `mqb_mini` с флагами `HttpOnly`, `SameSite=Strict`,
`Path=/` и `Secure` при HTTPS. Клиент не может прочитать её и не хранит секрет в
URL, `localStorage` или `sessionStorage`. Cookie автоматически отправляется на
same-origin API; для изменяющих запросов клиент добавляет `X-Mini-CSRF: 1`, а сервер
сверяет точный `Origin`. Для совместимости внешние интеграции пока могут использовать
`Authorization: Bearer …`; этот путь не применяется приложением в браузере.
Сессия действует 15 минут, продлевается явной командой renew и сохраняется при рестарте.
В БД находятся только SHA-256 токена и fingerprint подписанного входа, не сырой
`initData`, не bot token и не plaintext bearer. Ответы имеют `Cache-Control: no-store`.
В PostgreSQL хранится только digest токена; сырой credential не попадает в тело ответа.
Bearer-путь оставлен для переходной совместимости, его отключение требует отдельной
миграции API-клиентов.

Один подписанный вход обменивается только один раз, в том числе при конкурентных
запросах. Повтор — 409, необходимо заново открыть Mini App и получить свежий
`initData`. Если ответ login потерян в сети, повтор не раскрывает прежний bearer.
До пяти входов за 15 минут на игрока; после достижения — 429. Отозванный вход
остаётся в БД до истечения срока для защиты от replay.

`DELETE /api/mini/session` отзывает текущую сессию. Каждый запрос перепроверяет
бан и revision пользователя; ban → unban не оживляет старую сессию. Смена
`MINI_APP_BOT_TOKEN` также инвалидирует прежние сессии этого сервиса.

| `POST /api/mini/mafia/chats/{id}/discussion` | Сообщение участника в лобби/дневной фазе; обязательный `Idempotency-Key`, максимум 1000 символов |
| `POST .../action`, `POST .../vote` | Тайный ход/голос проверяется по `phase_revision`; независимые действия одной фазы не инвалидируют друг друга |
| `POST .../advance` | Переход ведущего проверяется по общей `revision`; смена фазы увеличивает также `phase_revision` |
| `POST .../restart` | Реванш тем же составом после завершения, только ведущим |

Для Mafia `lobby.revision` меняется при любом изменении состояния; `phase_revision`
служит fence только для тайного действия или голоса и меняется при переходе фазы.
Переходный API пока принимает поле `expected_revision` и для действий трактует его
как `phase_revision`; клиент должен отправлять соответствующее поле из проекции.
Повтор `command_id` возвращает результат только при полном совпадении игры,
участника, вида команды, версии и payload.
Обсуждение хранится как публичные события игры, не меняя фазу или ревизию;
Mini App выводит текст без интерпретации HTML.

Пагинация списков: `limit=1..50`, `offset=0..10000`, результат `items/has_more`.
Равные баллы дают одинаковое место, порядок стабилизирован ID. Заблокированные
профили исключаются из рейтинга API, поэтому он может отличаться от legacy-вывода.
ID и баллы передаются строками без потери точности.

`/chats` — **история**, а не доказательство текущего членства. Для группы поле
`membership_verified=false`. При выборе группового рейтинга/игры требуется:

1. Своя запись участия, известный group/supergroup, активный и незаблокированный чат.
2. Свежая проверка `getChatMember`: бот — администратор, пользователь — текущий
   участник (restricted разрешён только с `is_member=true`). Положительного кеша нет.
3. Повторная проверка пользовательской сессии и доступа к чату после сетевого ожидания.

Старая запись `ChatMember`, переданный клиентом ID или даже подписанное поле `chat`
не заменяют проверку. Метод Telegram гарантирован для чужих участников только
при админских правах бота. [Контракт Telegram](https://core.telegram.org/bots/api#getchatmember).
Ошибка/429/timeout проверки — 503, не разрешение доступа. Бюджет проверки — до
8 секунд, автоматических сетевых повторов нет. Личный чат доступен только владельцу.

Чужая персональная фото-серия скрыта даже от другого участника той же группы.
В ответ игры никогда не включаются вопросы, верные варианты, пояснения, подсказки,
пути медиа, чужие результаты и сырой checkpoint. Просмотр состояния сам по себе
не запускает jobs и не изменяет очки. Историческая неполная фаза помечается unavailable.

`GET /api/mini/chats/{id}/details` возвращает `can_edit=true` только владельцу личного
чата или подтверждённому Telegram-создателю/администратору группы. Групповые настройки
сохраняются через тот же revisioned `SettingsService`, что и настройки бота; обычные
участники видят только доступную им статистику и не могут менять параметры чата.

## HTTP и эксплуатационные ограничения

- Единственный явный origin; межсайтовые запросы запрещены, CORS не включён.
  Cookie админки и bearer Mini App не взаимозаменяемы.
- HTTPS обязателен; HTTP разрешён только при offline=true и loopback-клиенте.
  Offline не ослабляет подпись/сессию и **не** разрешает групповой доступ.
- Login: JSON до 20 КБ, initData до 16 КБ/32 полей. Ошибки не отражают credentials.
- На процесс: до 600 запросов/мин, на IP до 120 обычных запросов или 10 запросов
  к session/мин. Память ограничена общим лимитом. Это не распределённая защита:
  перед публикацией нужны ingress-лимиты, таймауты и согласованный proxy trust.
- Чтения используют согласованный read-only PostgreSQL snapshot. Запрос,
  начавшийся до блокировки, может успеть завершиться; новый запрос её увидит.
- Таблица сессий очищается от истёкших строк при последующих входах. Баллы,
  ответы, игры и журнал администратора этой очисткой не затрагиваются.

Для отдельной роли Mini App нужны CONNECT/USAGE соответствующей БД/схемы,
SELECT на `users`, `chats`, `chat_members`, `quiz_sessions`, а также
SELECT/INSERT/UPDATE/DELETE на `mini_app_sessions`. Гостевой вход и сохранение
«Алхимии» дополнительно требуют SELECT/INSERT/UPDATE на `accounts`,
`guest_sessions`, `alchemy_progress`, `alchemy_craft_commands`; выход отзывает строку
в `guest_sessions`. Импортная Telegram-синхронизация «Алхимии» не меняет рейтинг.
Только проверенная craft-команда обновляет `users.global_score` и пишет достижения,
поэтому ей нужны соответствующие права на `users` и `achievement_grants`.
Конкретные GRANT для production-роли нужно проверить
перед запуском: отдельной роли в репозитории пока нет. Миграции запускает
владелец схемы, не публичный сервис. В dev используется роль `mqb_dev` на
55433. Pytest работает в отдельной базе `morning_quiz_test` того же контейнера.

После восстановления production backup нужно отозвать восстановленные Mini App
сессии (`revoked=true`), чтобы не оживить ранее завершённый вход. Это отдельный
шаг будущего runbook, не удаление истории игроков. Не включать транспортный debug
и логирование request body/Authorization без удаления секретов.

## Локальный запуск (PowerShell)

```powershell
Set-Location 'C:\Users\Lizard\Projects\morning-quiz-bot'
# .venv-local уже подготовлена через Initialize-LocalEnvironment.ps1
pwsh -NoProfile -File .\scripts\Start-LocalMiniApp.ps1
```

Открыть `http://127.0.0.1:4185/app`: подключённый интерфейс с профилем,
достижениями, чатами, рейтингами, расписаниями и состояниями обоих игровых режимов.
Отдельная `web.dev_mini_app:create_dev_app` добавляет явный вход фиксированного
synthetic-игрока, только при dev-БД на 55433 и synthetic signing key. Публичная
`web.mini_app:create_app` этого входа не содержит. Скрипт создаёт демо-участника
без сброса уже накопленного прогресса. Настоящие Telegram-запросы отсутствуют.

Параметр `Start-LocalMiniApp.ps1 -PlayerId <ID>` выбирает существующего игрока
в dev-БД; UI явно обозначает локальный просмотр. Это не доказательство Telegram
идентичности. Параметр задаётся оператором, а не браузером; synthetic membership
по-прежнему действует только для фиксированного демо-игрока/чата.

Общий `Test-LocalMilestone.ps1` пересоздаёт только логическую БД тестов;
постоянная `morning_quiz_dev` отделена. Полная проверка и обычный pytest работают отдельно,
не затрагивая dev-прогресс; два UI можно оставить открытыми.

## Telegram-интерфейс и ограниченный HTTPS-тест

`GET /api/mini/config` возвращает только публичные параметры интерфейса:
`bot_username`, `game_location=telegram-chat`, `offline`, `private_test`.
Username задаётся серверной настройкой `MiniAppSettings.bot_username`;
test launcher получает его проверенным `getMe`. Секретов в этом ответе нет.

`/app/telegram-ui.js` обрабатывает тему, viewport, safe areas, BackButton,
SettingsButton, HapticFeedback и явный запрос fullscreen. LocalStorage содержит
только тему/выбор виброотклика; токен авторизации хранится в HttpOnly cookie.
При наличии
Telegram initData вход выполняется автоматически с прежними HMAC/TTL-проверками.

`create_app(..., allowed_user_ids={...})` дополнительно ограничивает вход и
каждый авторизованный запрос. По умолчанию дополнительного списка нет;
ограниченный test launcher всегда задаёт одного пользователя и запрещает группы.
Это не заменяет подпись или проверки доступа к данным.

`scripts/Start-LocalTelegramMiniApp.ps1` подготовлен для отдельного HTTPS теста
с разрешённым test bot. Upstream слушает 127.0.0.1:4187, доверяет forwarded headers
только loopback; содержит публичную фабрику, а не dev-login/админку. Сам launcher
не публикует ingress. После разрешения 2026-08-31 отдельный Quick Tunnel подключён
