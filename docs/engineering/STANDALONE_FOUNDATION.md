# Самостоятельный гостевой вход: первый вертикальный срез

После миграций `20261007_0014` и `20261007_0015` приложение создаёт независимый
`Account` без Telegram `User` или `Chat`. Гостевая сессия хранится в PostgreSQL:
браузер получает непрозрачную HttpOnly cookie на 30 дней, а БД хранит только
хэш. Повторное открытие и `/api/guest/resume` используют тот же аккаунт.

«Алхимия» сохраняет открытия по `account_id` в общей таблице прогресса. В
браузере локальное сохранение каждого гостя имеет отдельный ключ. Страница
получает идентификатор аккаунта от сервера до запуска игрового движка и
выбирает гостевой API независимо от оставшегося Telegram token. Гостевые
открытия не начисляют общие очки или награды и не попадают в рейтинг.

Для запуска без Telegram после миграций нужны `MINI_APP_DATABASE_URL`,
`MINI_APP_ORIGIN` и `MINI_APP_OFFLINE=1` для loopback HTTP. `MINI_APP_BOT_TOKEN`
оставить пустым. Запустить `python -m uvicorn web.mini_app:create_app --factory
--host 127.0.0.1 --port 4185 --no-proxy-headers`, затем открыть
`http://127.0.0.1:4185/app`. Миграции выполняет владелец схемы через
`python -m alembic upgrade head`. Для HTTPS использовать точный origin и
Secure cookie. Роль БД должна иметь права, перечисленные в
[`MINI_APP_API.md`](../MINI_APP_API.md).

Гость может создать приватную account-owned комнату и увидеть только комнаты
своего аккаунта через `/api/guest/rooms`; повтор с тем же UUID и названием
возвращает ту же комнату. Владелец может создать ограниченный по сроку и числу
использований код приглашения, посмотреть его метаданные или отозвать; сам код
показывается только при создании, а в БД хранится только его SHA-256. Другой
гостевой Account вступает по коду, не объединяя профили. PostgreSQL сериализует
расход последнего использования; повтор запроса уже вступившего Account после
потери HTTP-ответа идемпотентен. Поверх комнаты реализован самостоятельный
игровой сценарий «Мафии»; восстановление гостя после удаления cookie и привязка
к Telegram ещё не реализованы. Выход отзывает сессию; прежний гость после этого
недоступен.
Гостевой вход не объединяет аккаунты автоматически.

Миграция `20261008_0018` добавляет `AccountIdentity` и закрепляет Telegram ID
как внешний provider identity, а не как внутренний идентификатор приложения.
Для существующих пользователей миграция сохраняет их `User` и `Account`,
создаёт Telegram identity и заполняет `GamePlayer.account_id` вместе с
`actor_account_id` команд/событий. Новые партии через `GameRepository` разрешают
аккаунт по заблокированной Telegram identity. Конфликтующая или отозванная
identity не перепривязывается молча.

Это пока слой идентичности и аудита игровых акторов, не завершённый гостевой
gameplay или account linking. Миграция `20261008_0020` делает `Room` обязательной
областью игры, оставляет `games.chat_id` nullable для transport-neutral игры и
переводит `GamePlayer` на платформенный ключ `(game_id, account_id)`; Telegram
`user_id` сохраняется как nullable identity projection. Репозиторий умеет читать,
создавать и заменять room-only game без выдуманного чата. Mafia projections,
event actors и idempotency receipts теперь также допускают account-only запись;
Telegram ID остаётся необязательным identity projection. Это закрывает базовый
storage-контракт. Account identity collisions и замена существующей Telegram
identity без отдельного linking-flow отклоняются; создание/замена игры и
синхронизация проекций атомарны через savepoint. Mafia application commands
также оборачивают квитанцию, переход, событие и результат в одну атомарную
границу. Ниже приведён объём подключённого standalone-сценария и его оставшиеся
архитектурные ограничения.

Standalone Mafia использует существующие `MafiaApplicationService` и
`domain.mafia`, account actor приходит из авторизованной `RoomMembership`;
фиктивные Telegram IDs и копия игровых правил не используются. API комнаты
предоставляет лобби, приватную роль, обсуждение, ночное действие, голосование,
переход фазы и реванш. Mini App переиспользует общий экран/презентер игры с
отдельным room API scope. Записи игры, действий и событий остаются в PostgreSQL;
worker обрабатывает дедлайны room-only партий. Транзакционная HTTP-проверка
проходит гостевой цикл от приглашений и старта через ночное действие, дедлайн,
голосование и победу до реванша, при этом в базе нет Telegram `User`/`Chat`.

После миграции `20261008_0021` persisted Mafia state единообразно хранит
`room_id`, `host_account_id` и `account_id`; Telegram chat/user IDs остаются на
границе адаптера и в проверенных транспортных проекциях. Codec переводит legacy
state без потери дополнительных полей, а migration сначала проверяет весь
ростер и привязки всех Mafia games и только затем меняет state. Для локальной
dev-БД миграция применена; pre-upgrade архив восстановлен в изолированную БД и
сверен без изменения исходной. Domain-правила не синтезируют account ID из
числового Telegram ID. Между интерфейсами всё ещё нет полноценного linking гостя
и Telegram-аккаунта, поэтому перенос игры после linking пока не обещается. В
комнате также ещё нет настраиваемых временных правил/тихих часов, AFK,
выхода/паузы и передачи ведущего. Репозиторий берёт общий advisory lock и
ограничивает room kind/current game, но авторизацию выполняет application layer
через membership.

Для восстановления/привязки всё ещё нужен подтверждённый контроль обеих
идентичностей и явно выбранная политика переноса; совпадение имени или Telegram
ID из непроверенного запроса не объединяет аккаунты.

Disposable PostgreSQL milestone теперь проходит миграции с пустой схемы до
`20261008_0021`, `alembic check`, полный pytest, dump/restore и JS syntax.
Ручная проверка в Telegram WebView и браузере всё ещё нужна перед релизом;
также нужны отдельный безопасный linking/recovery flow и подтверждённая политика
переноса данных между аккаунтами.
