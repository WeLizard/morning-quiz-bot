# PostgreSQL: применение расписаний без перезапуска

Проверено локально 2026-08-30. Рабочий сервер не переключался. Это часть
[MQB-001](tasks/MQB-001-postgresql-and-mini-app-foundation.md), а не завершение релиза.

## Как это работает

1. Бот или локальная админка сохраняет настройки через `SettingsService`.
   Строка чата, `settings_revision` и `daily_schedules` изменяются одной транзакцией.
2. В PG-режиме бот при старте создаёт `ScheduleSync` и читает настройки из БД.
   Затем повторяет синхронизацию каждые 15 секунд через JobQueue. Изменения
   через меню бота также запрашивают синхронизацию после commit.
3. Из `Chat.settings` строятся планы квиза и мудрости с общим часовым поясом.
   `daily_schedules` — транзакционная проекция; прямое редактирование этой таблицы
   не является поддерживаемым способом управления расписанием.
4. Каждый план получает стабильный token из типа, часового пояса и отсортированных
   времён. Одинаковый план не создаёт новые jobs; пропавшие jobs создаются заново.
5. Перед запуском квиза и отправкой мудрости проверяется актуальный план из БД.
   Старая задача, отключённый, неактивный или удалённый чат пропускаются.
   После генерации AI-текста мудрость проверяет план повторно перед отправкой.

Квиз продолжает работать в Telegram-чате. Mini App для этого механизма не нужен.
Режим JSON сохраняет прежние планировщики; новый цикл включается только при
`STORAGE_BACKEND=postgres`.

## Изменение через локальный API

Получить `X-Settings-Revision` из `GET /api/chats/{chat_id}/settings`, затем:

```text
PUT /api/chats/-123/settings?expected_revision=4
Content-Type: application/json

{
  "daily_quiz": {
    "enabled": true,
    "timezone": "Europe/Istanbul",
    "times_msk": [{"hour": 9, "minute": 0}, {"hour": 18, "minute": 30}]
  },
  "daily_wisdom": {"enabled": true, "time": "10:00"}
}
```

Изменяются только переданные вложенные поля; остальные параметры сохраняются.
`times_msk` — историческое имя: времена трактуются в `daily_quiz.timezone`,
а не обязательно по Москве. Мудрость использует тот же часовой пояс.

HTTP 428 означает отсутствие версии, 409 — конфликт, 422 — неверные параметры.
Включённому квизу нужны 1–24 неповторяющихся времени. У отключённого квиза
допустим пустой список. Неизвестные часовые пояса и некорректные времена
отклоняются без частичного сохранения. В меню бота перед удалением последнего
времени включённого квиза требуется отключить квиз либо добавить другое время.

В старых данных встречается включённый квиз с пустым списком. При чтении
сохраняется прежнее поведение: нет запусков квиза, мудрость работает независимо,
данные автоматически не исправляются. Перед записью новых настроек расписаний
через API такой квиз нужно явно отключить либо указать времена в том же запросе.

Успешный PUT возвращает новую `revision` и `schedule_sync: "pending"`.
Это подтверждение записи в БД, **не подтверждение применения работающим ботом**.
Старые отдельные toggle/reset-маршруты ещё возвращают 501; используйте versioned PUT.
Фронтенд админки пока не адаптирован к этому протоколу полностью.

## Проверка применения

`GET /api/schedules/status` читает последний отчёт бота из `system_state`:

- `fresh` — отчёт не старше 45 секунд (три интервала синхронизации);
- `worker_status.checked_at` — время отчёта UTC;
- `worker_status.applied_revisions` — версии успешно обработанных чатов;
- `worker_status.failed_chats` — чаты с ошибкой и класс исключения;
- `worker_status.interval_seconds` — интервал проверки.

Нужно проверить `fresh`, отсутствие чата в `failed_chats` и совпадение его
применённой версии с текущей версией настроек. Свежий отчёт с ошибками не означает
успех. Старый отчёт не доказывает, что бот работает. Отчёт отражает установку
jobs, но не успешную доставку Telegram-сообщений.

## Сбои и границы гарантий

- Ошибка чтения БД не считается пустым списком чатов и не удаляет jobs.
  При недоступной БД callback не запускает квиз/отправку по старому кэшу.
- Для каждого планировщика сначала добавляются новые jobs, затем удаляются
  старые. Если добавление не удалось, созданные в этой попытке jobs убираются,
  старые сохраняются; следующий цикл повторяет попытку.
- Два планировщика не образуют одну транзакцию: квиз уже может быть обновлён,
  когда установка мудрости завершится ошибкой. Такая версия не отмечается
  применённой; старые callbacks защищены проверкой плана.
- Ошибка одного чата не останавливает обработку остальных. Невалидные старые
  настройки нужно исправлять явно, а не заменять молча значениями по умолчанию.
- Поддержан **один процесс бота**. Блокировка цикла локальная; распределённой
  аренды jobs, журнала запусков и гарантии exactly-once доставки пока нет.
- При полном рестарте будущие jobs восстанавливаются из настроек. Пропущенные
  во время остановки запуски не воспроизводятся. Для задержки уже существующей
  задачи применяется `job_grace_period_seconds` и coalescing.
- Проверка плана и Telegram-отправка не атомарны. Если отключение пришло уже
  после последней проверки или игра началась, оно не отменяет текущую игру/отправку.

## Часовые пояса и тесты

Оба планировщика используют именованный часовой пояс cron. PTB принимает его
через `time.tzinfo`: [JobQueue 21.7](https://docs.python-telegram-bot.org/en/v21.7/telegram.ext.jobqueue.html#telegram.ext.JobQueue.run_daily).
Время не фиксируется в UTC при создании задачи. Тест для 09:00 Europe/Berlin
проверяет 08:00 UTC зимой и 07:00 UTC летом на настоящих триггерах PTB/APScheduler.
Для неоднозначных/несуществующих локальных часов в ночь перевода действуют
[ограничения APScheduler 3.x](https://apscheduler.readthedocs.io/en/3.x/modules/triggers/cron.html#daylight-saving-time-behavior);
политика компенсации таких запусков отдельно не реализована.

`tests/test_schedule_sync.py` проверяет повторную синхронизацию, новый экземпляр
планировщиков после рестарта, восстановление пропавшей задачи, отключение,
неактивный/удалённый чат, ошибки БД и добавления jobs, устаревшие callbacks,
отключение во время генерации, вложенные API-правки и статус применения.
Отдельный тест меню защищает список времён от повторной записи строкой.
Проверена совместимость старого пустого списка времён без изменения данных.
Telegram и AI API заменены заглушками; реальный бот не запускается.

Команды запуска тестов — в [руководстве админки](POSTGRESQL_ADMIN.md#воспроизводимые-проверки-на-windows).
