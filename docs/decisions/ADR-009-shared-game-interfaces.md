# ADR-009: Бот и Mini App — два интерфейса одной игры

Статус: `superseded` решением [ADR-010](ADR-010-application-core-and-adapters.md).
Дата: 2026-08-31. Задача: MQB-003.

## Контекст

Пользователь уточнил: Mini App должен позволять играть и пользоваться функциями
бота, а не служить только профилем со ссылками обратно в чат. Правила, результаты
и доступные по роли настройки должны быть общими. Серверная админка остаётся локальной.

## Решение

Не создавать второй подсчёт очков или независимую реализацию фото-загадок.
Авторизованные действия приложения передаются существующему PTB application:
те же ConversationHandler, QuizManager, PhotoQuizManager, ScoreManager и PG services.
У приложения собственное отображение вопросов, кнопок, изображений и ответов.

`MiniBridge` хранит ограниченные mailbox/projection в `system_states`, ключ
разделён по боту и пользователю. Runtime публикует результаты только разрешённой
лички. API выдаёт белый список полей; правильный вариант/пояснение — лишь после
зафиксированного ответа данного игрока. Файловые пути и сырой checkpoint не выдаются.

Запросы имеют idempotency ID. Callback проверяется по сообщению, revision и
доступным кнопкам, голос — по опросу/варианту/дедлайну, фото-ответ — по текущему
раунду. Повтор с тем же ID не запускает второе действие; зависший running после
перезапуска становится uncertain, не исполняется заново автоматически.
Входы Telegram и Mini App сериализуются одним lock; начисления дополнительно
защищены существующим ledger. Проверка прав/maintenance остаётся в общих handlers.

App action не представляется входящим событием Telegram: в диагностике отдельное
`mini_app_action`. Подтверждение app callback остаётся локальным; ответное сообщение
не цитирует выдуманный Telegram message ID. Ответ из приложения начисляет результат
игры, но не голосует за пользователя в нативном Telegram poll.

Для одиночной игры, открытой из Mini App, private dev runner использует локальный
delivery adapter: результат существующего обработчика публикуется в MiniBridge, а
Telegram Bot API для вопроса, фото или результата не вызывается. Чатовый и будущий
групповой режимы используют обычную Telegram-доставку. Это переходный transport
adapter, не второй движок и не объявленная полная миграция доменной логики:
транспортно-независимый game service остаётся следующим отдельным шагом.
Групповое управление через Mini App ещё не подключено.

## Локальная проверка и ограничения

Preview 4185 запускает те же private handlers с OfflineRequest и фиксированным
synthetic пользователем, без настоящего токена и сетевого Telegram-клиента.
Тестовый публичный 4187 требует Telegram HMAC и отдельный allowlist; dev-login
там отсутствует. `runtime_enabled` включается явно этими двумя фабриками.
По умолчанию публичная фабрика остаётся без игровых mutations.

Не добавлены схема, миграция, удаление или пересчёт старых результатов.
Общие роли/группы, отдельная DB role для mailbox и production ingress требуют
самостоятельной приёмки. Этот механизм включён только в dev runners, не в production.

## Проверка

`tests/test_mini_bridge.py`: приватность mailbox, запрет подмены действий,
идемпотентность, отсутствие спойлеров, shared classic → ответ → Telegram duplicate,
фото → изображение → текстовый ответ, сохранение имени, настройки и отсутствие
фиктивного reply-to. HTTP smoke: `scripts/check_mini_app_play.py`.
